# Threat model

<!-- doc-rev: 20 -->

[Documentation](README.md) · [한국어](ko/THREAT_MODEL.md)

This is version 0 of the living threat model for Hopae: the assets, the
actors, the entry points, a STRIDE pass over each request flow of the
[architecture](ARCHITECTURE.md#request-flows), and the mitigations the design
relies on. Every security-relevant change updates this page in the same
change. Threat identifiers (`TM-nn`) are stable and are referenced from
scenarios and ADRs.

## Assets

| Asset | Where | Loss means |
| --- | --- | --- |
| Session handles (cookie values) and portal transactions | Browser cookies; store as digests | Impersonation on one host (handle) or completion of someone else's login (transaction) |
| Handoff codes | URL for ≤ 60 s; store as digests | Impersonation on the target host if replayable |
| Identity headers | Gateway → upstream only | Any application trusting a forged header is fully compromised |
| Provider credentials (client secrets), SMTP credentials, webhook secrets, caller key | Environment at run time | Impersonation of Hopae toward providers; forged webhooks |
| User directory and login history (personal data) | Primary store | Privacy breach; account takeover via linking |
| Policy (apps, binding, blocks, step-up) | Primary store and configuration | Silent loosening of access |
| Release signing seed and update manifests (M6) | Offline with the maintainer | Supply-chain compromise of every instance |
| Availability of verify | Hopae process, store | Every protected application is unreachable (fail closed) |

## Actors

| Actor | Capability | Not assumed |
| --- | --- | --- |
| Anonymous internet client | Any HTTP request to the gateway's public listeners; many IPs; chosen `Host`, cookies, headers, query strings | Breaking TLS; reading another user's browser |
| Authenticated user | A valid session; a browser that can be scripted by a malicious page on another origin | Access to the gateway network |
| Malicious sibling site | Control of a host on a sibling subdomain or on the same registrable domain as an application | Control of the application host itself |
| Compromised application | Full control of one upstream and its responses | Access to Hopae's listeners or the store |
| Network attacker between gateway and Hopae | Only if the private network is misconfigured; the design treats it as out of scope but limits damage with HC-3 | — |
| Malicious identity provider or a confused one | Returns arbitrary claims, mixes up clients, is slow or down | Forging another provider's signatures |
| Administrator or viewer holding a console grant (M4-min) | Every console action: disable users, end sessions, read every user's email, client addresses and history; a compromised administrator session acts as the administrator until the grant or session is revoked | A second credential system; storage of its own; access to the store outside Hopae |
| Lua script author (M5) | Arbitrary scripts within the sandbox | Escaping the process sandbox |
| Supply chain | Malicious crate update, malicious release asset | Possession of the signing seed |

## Entry points

| Entry point | Listener | Reachable by | Notes |
| --- | --- | --- | --- |
| `GET /_hopae/verify` | Gateway listener | Any process in the gateway's network namespace can connect; only callers presenting the caller key (HC-3) are served | Highest request rate; every protected request |
| `GET /_hopae/login`, `GET /_hopae/logout` on every protected application host | Gateway listener, through the protected route's verify call | Internet, as document navigations on the application host | Answered by Hopae with a relayed `302` or `403`, never `2xx`; the whole `/_hopae/` namespace is reserved and never reaches the upstream ([ADR-0015](adr/0015-app-host-entry-points-and-upstream-cookie-stripping.md)) |
| `GET /login`, `POST /login/<p>`, `GET /callback/<p>`, `GET/POST /logout[?txn=]`, `GET /stepup*` | Portal listener via the portal route | Internet | Browser input only |
| `GET/POST /security*`, `POST /stepup/webauthn`, `GET /assets/webauthn.js` ([WebAuthn passkeys](WEBAUTHN.md)) | Portal listener via the portal route | Internet; only with `webauthn` configured (otherwise `404`) | Live portal session required; CSRF and exact `Origin` on every POST; ceremony state server-side and single use; the only portal pages that run script |
| `GET /healthz` | Portal listener | Internet via the gateway | No secrets |
| Console pages and `/v1/*` API (M4-min) | Admin listener (`listen.admin`) | Internet, through the gateway's protected route for the console host; any process that can reach the listener | Hopae authenticates every request from its own session handle and the grant table; injected identity headers are never read; CSRF and origin checks; roles ([administration](ADMIN.md)) |
| Outbound: provider discovery, JWKS, token, user info; SMTP; webhooks | Hopae → internet | — | SSRF and response-size controls |
| Store connections | Hopae → SQLite file, PostgreSQL, Redis | — | Private network; TLS for remote Redis/PostgreSQL |
| Configuration file and environment | Process start, reload (M6) | Operators | Validated; secrets by reference |
| Update manifests and assets (M6) | Hopae → GitHub releases | — | Signed envelope |

## Threat catalogue

Severity follows the process scale (S1 bypass of a security boundary … S4
cosmetic). "Scenario" names the scenario that exercises the threat.

| ID | Threat | Flow | STRIDE | Mitigation relied on | Scenario |
| --- | --- | --- | --- | --- | --- |
| TM-01 | Open redirect through return URLs: an attacker crafts a login link whose return target points off-site | 1, 3, 4 | Tampering, Spoofing | The portal never reads a return URL from the client. The target is taken from the gateway-generated `x-original-url` of the verify call, stored in the transaction, validated (absolute, allowed scheme, host registered or default-allowed, ≤ 2 KiB, no userinfo, no fragment) and only ever emitted as `Location` to that host. The handoff `302` targets the exact URL the gateway reported minus the parameter. The application-host entry points accept a `return` only on the request's own registered origin, and the target reaches the portal inside a transaction (the logout ticket), never as a URL. | 005, 015 |
| TM-02 | Cookie tossing: a sibling subdomain sets a cookie that the application host presents as its session | 4, 5 | Spoofing | `__Host-` prefix: browsers reject such cookies with a `Domain` attribute and never send a sibling's host-only cookie. Unknown handles are never adopted; handles are minted server-side only at handoff. Development mode without the prefix is documented as insecure. | 009 |
| TM-03 | CSRF on login, switch and logout: a malicious page starts a login as the attacker (login CSRF), switches the account, or logs the victim out | 2, 3, 6 | Spoofing, Tampering | `POST /login/<p>`, `POST /switch` and `POST /logout` require a CSRF token bound to the `__Host-hopae_portal` or `__Host-hopae` cookie and an `Origin` equal to the portal origin. The callback locates the transaction by `state` and requires the browser's portal binding cookie to match the digest the transaction recorded at its first visit, so a victim cannot be made to complete an attacker's transaction. `GET /logout` and `GET /switch` only render a form. The application-host `GET /_hopae/logout` only creates a logout ticket and redirects to that form: it clears no cookie and revokes nothing; a non-document request to it is a `403` without `set-cookie`; the optional no-confirmation mode acts only on `sec-fetch-site: same-origin`, a forbidden header browsers compute over the whole redirect chain. `SameSite=Lax` cookies. | 002, 006, 015 |
| TM-04 | Session fixation: the attacker fixes a known handle or transaction in the victim's browser before login | 2, 3, 4 | Spoofing | Handles are created only by Hopae at handoff and stored as digests; a client-presented unknown handle is ignored. The transaction cookie is replaced at `/login` and cleared at completion. A new session gets fresh handles on every host; the portal handle is reissued at login. | 002, 003 |
| TM-05 | Handoff code replay or theft (history, logs, Referer, shoulder surfing) | 4 | Spoofing, Repudiation | Single use with an atomic conditional consume; 60 s lifetime; bound to the target host, path, the client IP and the browser binding cookie planted on that host when the login started; carries its issuance level and the session's credential generation; redeemed by document navigations only; consumed through the gateway only (the gateway sets `referrer-policy: no-referrer` on the relayed `302`); rejection burns the code, emits `handoff.rejected` and counts toward per-IP throttling (M2). The code never reaches the upstream. | 003 |
| TM-06 | Identity header spoofing: a client sends `x-forwarded-user` or a gateway context header | 5 | Spoofing | The gateway strips every declared identity name from every incoming request and regenerates `x-forwarded-*`/`x-original-*`. Hopae's gateway listener is unreachable from clients; its portal listener ignores `x-forwarded-*` from non-trusted proxies. Scenario 007 proves a spoofed header never reaches the upstream. | 007 |
| TM-07 | Verify endpoint denial of service: floods of random handles or long cookies; slow store | 5 | Denial of service | Verify does no provider calls and one indexed lookup; cookie header ≤ 8 KiB and handle format checked before hashing; bounded negative cache for unknown handles; concurrency limit on the gateway listener with `503` when exceeded (fail closed, counted); store timeouts; the gateway's `timeout_ms` bounds the client's wait; the gateway's rate limits and failure bans as outer layers. | 004 |
| TM-08 | Provider mix-up: the callback for provider A is completed with artifacts from provider B, or a token endpoint is chosen from attacker data | 3 | Spoofing, Elevation | Each transaction records the chosen provider; the callback path names the provider and must match; `state` is bound to (transaction, provider); endpoints come only from the provider's own configuration or discovery document fetched from the configured issuer; ID token `iss` and `aud` are checked against the provider's configuration; distinct `redirect_uri` per provider. | 002, 012 |
| TM-09 | Account takeover by email collision: provider B asserts the email of a user created through provider A, including a reassigned mailbox that the provider still reports as verified | 3 | Spoofing, Elevation | Linking policy ([ADR-0011](adr/0011-account-linking-policy.md)): by default an identity attaches to an existing account only after a fresh authentication with that account's existing method (`link_required`); a provider's `email_verified` is never sufficient; automatic linking is an opt-in restricted to authoritative emails (Google with `hd` in an allowlisted domain, Hopae's own email link); Kakao and Naver never auto-link. Email changes at a provider never move an identity between users; mailbox reassignment is recovery, not identity. | 002 (M1), 2xx (M3) |
| TM-10 | Webhook SSRF (M5): a destination points at an internal address or redirects there | — | Information disclosure, Elevation | Destinations must be `https`; the resolved address is checked against loopback, private, link-local and multicast ranges and pinned for the connection (no DNS rebinding); redirects are not followed; bounded body and timeouts; HMAC-signed payloads; destination list is administrator-only. | 44x (M5) |
| TM-11 | Lua sandbox escape (M5) | — | Elevation | Scripts run in separate worker processes with the gateway's model: `env_clear`, rlimits, seccomp allowlist, string/table/math libraries only, instruction and memory budgets, hard timeout with `SIGKILL` and respawn; inputs are copies, outputs validated; no network, secrets or filesystem. | 40x (M5) |
| TM-12 | Secret or token leakage in logs, events, error pages or the configuration API | all | Information disclosure | Logs and events carry identifiers only; handles, codes, tokens and passwords are never logged; the configuration references secrets by environment variable name; error pages are generic; `hopae --check` prints no secret values. | 013, 014 |
| TM-13 | Stolen cookie reuse from another network or device | 5 | Spoofing | Context binding ([ADR-0007](adr/0007-context-binding-policy.md)): per-application IP and UA binding with session termination on mismatch; idle and absolute lifetimes; `HttpOnly`; `Secure`. | 010, 011 |
| TM-14 | Direct access to the gateway listener (verify, invalidation) from a client or from another local process or container that shares the gateway's network namespace | 5 | Spoofing, Elevation | The caller key `x-hopae-gateway-key` (HC-3, required in M1) is compared in constant time before any header is read or any state touched; the listener is additionally bound to the host loopback and never published; the deployment template places Hopae in the gateway's network namespace or publishes the port on the host loopback only; the portal listener answers `404` for `/_hopae/verify`. | 004, 013 |
| TM-15 | Management plane abuse (M4-min): a user without a grant reaches the console, a read-only administrator performs a mutation, an administrator locks the deployment out by disabling themselves, CSRF on console forms or on the JSON API, a bootstrap that trusts a secret in a file, a grant resurrected from the configuration file after a runtime revocation | C | Elevation, Tampering | No separate credential system: administrators are users with a row in `admin_grants`, read from the primary store on every request (no cache); roles `admin` and `viewer` (read-only administrator), a viewer's mutation is refused and recorded; forms carry a CSRF token bound to the presented handle with an `Origin` check, JSON mutations require `content-type: application/json`, a custom request header and a matching `Origin`/`sec-fetch-site` when present, over `SameSite=Lax` cookies; self-disable is refused (`self_target`); bootstrap and recovery are `hopae admin grant` or the file's `admin.users[]` against the store (no token, no password), both binding a grant to a user id resolved once (TM-46); file seeding follows the provider import rule with `managed_by` and tombstones, so a revoked grant is never resurrected and an entry removed from the file is revoked; every denial is an `admin.denied` event ([ADR-0016](adr/0016-management-console-minimum.md)). | 300, 305 |
| TM-16 | Supply chain: malicious dependency or release asset (M6) | — | Tampering | `cargo audit` in G6, `--locked` builds, dependency justification; Ed25519-signed manifests, downgrade refusal, size and redirect bounds, offline signing seed. | 5xx (M6) |
| TM-17 | Enumeration and brute force: user existence from timing or messages; password or code guessing (M3) | 2, 3 | Information disclosure, Spoofing | Constant-work responses (dummy hash); uniform messages; per-account and per-IP throttling with lockout (M2); magic-link and TOTP rate limits. The portal's `txn` id is a 128-bit random value. | 1xx, 2xx |
| TM-18 | Stale allow after revocation when a decision cache exists (HC-1 or a Hopae-local cache), including replay of a cached allow from another client IP or another application on a shared route, refills from a nearly-expired tier, and a shared cache that keeps answering after the primary store revoked | 5, 6, 7, 8 | Elevation | Every TTL defaults to `0` (zero trust); Redis never holds session or decision state; the gateway key includes configuration generation, route id, resolved client IP, external scheme and authority and the listed-header digest; handoff requests bypass the cache under the shared recognition rule; `no-store` on every path-dependent and negative decision; an absolute `x-hopae-fresh-until` deadline anchored to the authoritative read and capped by session expiry obeyed by every tier; `x-hopae-gen` provenance on every allow so a subscriber discards fills older than the generation it last saw; the declared bound is the sum of the configured TTLs and is printed by preflight. | 1xx (M2) |
| TM-19 | Gateway and Hopae version mismatch producing a silently wrong contract | 5 | Tampering, Repudiation | Contract version header (HC-3) and a published compatibility matrix; unknown major → `400` → gateway `503` (fail closed); missing required context headers → `400`. | 004, 013 |
| TM-20 | Transaction or handoff flooding exhausting the store | 1, 4 | Denial of service | Transactions and codes have short TTLs and are pruned; per-IP creation caps; bounded table sizes with oldest-first eviction counted as `txn.evicted`; a `401` creates no transaction at all, so non-document floods write nothing. | 001, 004 |
| TM-21 | Unauthenticated `401` JSON leaking a portal transaction URL to a cross-site caller | 1 | Information disclosure | The `401` body names only the application URL the client itself requested (the document bootstrap); it creates no transaction and plants no cookie; no user data in the body. | 001 |

| TM-23 | A handle or a handoff code obtained before a step-up inherits the session's elevation | 9 | Elevation | Handles and codes carry `issued_aal`; codes also carry the session's `cred_gen`; the elevation transaction revokes every handle and consumes every outstanding code; redemption checks the generation and issues `min(code level, session level)`, so a pre-elevation code is dead or mints a level-1 handle that the elevation revokes. | 003, 004 (schema), 47x (M5) |

| TM-26 | Attacker-chosen return origin on a host-neutral route: the gateway generates `x-original-url` from a client-supplied `Host` | 1, 3 | Tampering, Spoofing | The return-origin allowlist is exactly the registered application host names and ports; there is no "any host" and no suffix mode; an unlisted host is denied before a transaction exists. | 005 |

| TM-31 | Concurrent tabs or an invalid-code XHR reset the browser's binding or transaction cookie, or two tabs race the very first cookie response, so an in-flight login of the same browser fails or an attacker can deny logins | 2, 4 | Denial of service | Binding and portal cookies are stable per browser and shared by all transactions; no response clears or replaces an existing well-formed value; redemption is document-only; a consumed code with its own handle answers an idempotent clean redirect; the first-use race recovers through the ordinary unauthenticated `302` and portal single sign-on (or a CSRF-protected retry at the portal), bounded by `handoff.max_recoveries` so it cannot loop. | 002, 003, 009 |
| TM-32 | A sink that stalls, or a receiver that never acknowledges, grows the event or delivery tables without bound until authentication writes fail | 2, 3 | Denial of service | Per-sink pending backlog cap with dead-lettering (`failed`, `backlog_overflow`), bounded retries; pruning every `prune_every` inserts or 60 s regardless of delivery state (table ≤ `max_rows + prune_every`); delivery rows cascade with their event and terminal rows expire on their own retention; failures stay visible through metrics and `sink.*` events. | 014 |
| TM-33 | A silent account switch, or no way to switch: a browser holding user A's handle on an application is handed user B's session | 4 | Spoofing | Unsolicited replacement is refused; the portal's `/switch` page shows host and both accounts and requires a CSRF-protected confirmation; confirming revokes only the handle the browser itself presented. | 003, 006 |
| TM-34 | A provider removed at run time is resurrected from the configuration file at restart | 2 | Elevation | Runtime removal leaves a tombstone row that the import skips; only an explicit `--force` import, recorded as an administrator event, reasserts the file. | 013 |
| TM-35 | Caller-key rotation causes an outage window during which every verify is refused, tempting operators to disable caller authentication | 5 | Denial of service | Hopae accepts a current and a next key; the documented sequence keeps every gateway/Hopae generation mix authenticated; preflight warns about a stale next key. | 004, 013 |
| TM-36 | An encoded alias of the reserved parameter (`%5Fhopae%5Fhandoff`), a duplicated parameter, or a non-document request carrying the parameter with a valid handle lets the code reach the upstream or confuses redemption | 4, 5 | Tampering, Information disclosure | One recognition rule (decoded query names; ambiguity rejected) is used by both redemption and the HC-1 bypass; the gateway also bypasses on the raw or encoded name in the path; a non-document request carrying the parameter is stopped with a relayed `403 handoff_parameter_not_allowed` before any upstream dispatch, code and cookies untouched; a primed-cache regression test. | 003 |
| TM-37 | Generation rollback after a database restore: a subscriber remembers higher generations than the restored Hopae reports, so fills are rejected and caching is suppressed, or a restore procedure that resets marks lets old in-flight work refill caches (*later*: no cache exists in M1) | 5 | Denial of service, Elevation | Generations are scoped by a database epoch regenerated by the restore procedure; subscribers keep marks per epoch and purge on an unseen epoch; in-flight work from the old epoch can never fill a new-epoch entry ([ADR-0006](adr/0006-verify-caching-and-invalidation.md) decision 8; HC-1/HC-2 criteria). | 1xx (M2) |

| TM-39 | Case-variant bypass of path-scoped protection: the gateway matches `path_prefix` byte-exactly, so `/ADMIN/x` misses the protected `/admin` route, falls to the public host route and reaches the upstream with no session; a case-insensitive upstream then serves the admin area unauthenticated. Hopae never sees the request. | 5 | Elevation | Deployment rule until HC-10: path-scoped protection only in front of a case-sensitive upstream, otherwise protect the whole host (the contract's fragment page says so). Gateway change HC-10 makes protected prefix routes match ASCII-case-insensitively by default. Hopae's own path rules (step-up, M2 path policy) compare the canonical path ASCII-case-insensitively so they cannot be bypassed the same way. Scenario 008-A1 records the fall-through against a live gateway so the exposure is visible until HC-10 flips its assertion. | 008 |
| TM-40 | The session handle and the binding cookie reach the application in the `cookie` header of every authenticated request (seen live on the reference deployment): an application that logs request headers, or a compromised one, holds a replayable credential for its own host that outlives the request | 5 | Information disclosure, Spoofing | Gateway change HC-12: the route-level `strip_request_cookies` (on public routes too; `auth.strip_request_cookies` is an alias) removes the configured handle and binding cookie names from the `cookie` header the upstream receives, after the verify call and every other header change, dropping the whole header on ambiguous syntax; `hopae --check` prints the field in the route fragment and the phase-1 drift report flags its absence. | TM-41 | Abuse of the application-host entry points: a cross-site page or a sibling subdomain logs the victim out through `/_hopae/logout` (logout CSRF), `return` becomes an open redirector, a case or encoding variant or a sub-path of `/_hopae/` reaches the upstream, a non-document request (`<img>`, fetch, prefetch) starts a redirect or clears a cookie, or an attacker-minted logout ticket is redeemed by the victim | 1, 5, 6 | Spoofing, Tampering, Elevation | The namespace is matched on the canonical path ASCII-case-insensitively; every reserved path that is not an entry point and every non-document request to an entry point is one `403` without `set-cookie` and without state; `return` must be the request's exact registered origin, carry no reserved parameter and name no reserved path, else `403`; the logout `GET` clears nothing and revokes nothing — the only state change is the portal's `POST` with CSRF token, `Origin` and either a valid portal handle or a single-use ticket whose portal-binding digest was recorded at the browser's first visit; the no-confirmation mode accepts `same-origin` only and, being opt-in, accepts same-origin navigation gadgets as a residual risk that `hopae --check` warns about; the logout ticket is a documented transferable revocation capability whose reach is limited to the session it names and the confirming person's own; after a logout the portal renders a signed-out page with a "Sign in again" link (validated like any return target) instead of redirecting to the protected target, so a provider with a live session cannot silently sign the user back in, and the signed-out reference is the consumed ticket, never a URL in a query; none of these outcomes is `2xx` (004-11). | 015 |
| TM-42 | Admin listener reached without the gateway: a local process, a container in the same namespace or a misrouted request presents injected identity headers (`x-forwarded-user`), forged gateway context or a spoofed client address to the console | C | Spoofing, Elevation | The admin listener derives identity only from the host-bound `__Host-hopae` handle evaluated by the verify engine (session, timers, binding, user status, application policy, freshness) and the grant table; identity headers and gateway context other than the forwarding headers are never read (boundary lint); a TCP peer outside `trusted_proxies` is refused before any cookie is read under the default `admin.untrusted_peers = refuse` (logged and counted, so a wrong deployment fails loudly) or treated as the client under `as_client`; forwarding headers from a trusted peer only feed client binding; a request without a valid console handle is `403 login_required` with no state change and no login started, counted and sampled through the same denial helper as the gateway listener; the listener is bound to loopback and the gateway's protected route performs its own verify first. | TM-43 | Stale administrator authority: a revoked grant, a disabled or demoted administrator, a sign-in that happened long ago (or a "fresh" sign-in the provider completed silently from its own live session, or one whose `auth_time` claim was absent or invalid) keeps acting through a live session, or acts between the request check and the write with a credential that expired — by its stored deadline or by a policy shortened since — or an authorization version that moved meanwhile | C | Elevation | The grant is read per request from the primary store; `users.status` and `authz_version` are read by the engine per request and the implicit `admin` application uses `on_authz_change: terminate`; `admin.max_auth_age` is evaluated at every console verify with one freshness predicate (`auth_time ≤ now + 60 s` and `now − auth_time < N`) shared by the engine, the listener and the fence; every session records `auth_time_source` (`provider_claim` or `hopae_completion`), an invalid claim fails the login instead of becoming `now`, and what freshness means depends on the provider's declared `reauth` capability: with a `max_age` provider the console requires a provider claim and, when stale, sends the browser to a reauthentication that **the session's own provider** performs (`max_age`, `prompt=login`, `auth_time` required and checked; another linked provider cannot refresh the evidence of an existing session, only create a new one); with an `unsupported` provider (the `google` preset) freshness is **Hopae login age** only; `admin.max_auth_age` is at least `30m` so a successful reauthentication always reaches the console within the transaction lifetime (ADR-0016 decision 15); ## Residual risks and open questions

- A compromised application can read its users' identity headers and `x-hopae-session`; it cannot mint sessions. The reviewer found no takeover path from the identifier alone; hashing it per application remains open.
- Strict IP binding terminates sessions for mobile users on network change; the default is strict as directed, and the operator may relax it per application. The threat model treats relaxation as an accepted risk, not a defect. Shared NAT means an IP is never a browser identity, which is why the handoff is bound to a browser cookie.
- The handoff code appears in the gateway's access log for its lifetime. The log is an operator asset; the code is single use and useless without the binding cookie.
- `x-original-*` headers sent by a browser reach the portal unchanged on an unmodified gateway; the portal never reads them (HC-9 would strip them).
- An attacker holding a stolen cookie can, under `terminate_session`, log the victim out once per login by presenting it from another IP; an accepted cost of the strict default.
- A registered host whose DNS the operator lets dangle is an open credential destination (TM-30); the drift check and the optional first-handoff confirmation reduce, but cannot remove, this operator duty.
- Event delivery is at-least-once: a log line or a webhook may repeat after a crash; receivers deduplicate by `event_id`.
- Provider deletion tombstones (TM-34) keep an API-managed id reserved for the life of the database; reusing the id requires `--force`.
- Without HC-12 the binding cookie and the session handle are sent to the application host in the ordinary `cookie` header of every authenticated request (TM-40), and script on that host can pre-seed a missing binding cookie; both are same-host trust, not cross-host escalation. With HC-12 neither cookie reaches the upstream of any route that sets `strip_request_cookies`; the field is route-level and must be set on the public routes of a path-scoped host too, which receive the `Path=/` cookies as well; the pre-seeding remains.
- With `apps[].logout_confirm = false`, an application that prerenders its own `/_hopae/logout` link (speculation rules) logs its users out on hover: a prerender is a same-origin document navigation and `sec-purpose` is not among the forwarded headers. The default keeps the confirmation; forwarding `sec-purpose` is a backlog item.
- After a confirmed logout the portal shows its signed-out page with a "Sign in again" link; nothing redirects to the protected target, so a provider that re-authenticates silently cannot sign the user back in without a click.
- `apps[].logout_confirm = false` trusts the application's own origin (TM-41): a same-origin navigation gadget in the application (a page that assigns a URL from its own query to `location`, such as `/continue?next=/_hopae/logout`) ends the user's session without a click, because a navigation started by a loaded document of the application's origin presents `sec-fetch-site: same-origin`. The mode is opt-in and `hopae --check` warns for every application that sets it.
- A logout ticket is a transferable revocation capability: one nobody opened can be given to another person, whose first portal visit binds it to their browser; their confirmation ends the session the ticket names (its creator's) and their own portal session, only reducing access (scenario 015-A9).
- Every handoff is delivered to `/_hopae/login`, so a path-scoped host needs the `site-hopae` route for login to complete, not only for the entry points.
- On a path-scoped host the `/_hopae` route is subject to TM-39 like any prefix: until HC-10 a case variant such as `/_HOPAE/logout` falls through to the public route and reaches the upstream, where it is an ordinary `404`, not an entry point.
- Someone who knows a live handoff code can submit it with a wrong bind and burn it, costing the legitimate browser one recovery round trip; the session and existing cookies are unaffected (availability only).
- Path-scoped protection is only as good as the gateway's route selection: until HC-10, a case-insensitive upstream behind a prefix route is exposed to case variants (TM-39), which Hopae cannot see; whole-host protection is the safe default.
- Until Hopae has its own second factor a console session is single-factor (TM-43): a phished or replayed provider login is an administrator login. The documented mitigations are a second factor enforced by the provider for administrator accounts, the freshness rule after `admin.max_auth_age` (a provider-verified reauthentication with a `max_age` provider; **Hopae login age only** with an `unsupported` provider such as Google, where the provider may complete the new sign-in silently from its own session), the implicit application's short lifetimes and strict binding, and revocation through the CLI or the file. A session that authenticated recently on another host enters the console by single sign-on without a new challenge; the bound, not the entry, triggers the challenge. TOTP for administrators is proposed as the milestone after M4-min.
- The admin listener cannot authenticate the gateway (no static upstream header exists and a local process shares the loopback address); `admin.untrusted_peers = refuse` makes an unexpected peer fail loudly but cannot tell a local process on the gateway's own address from the gateway, so a local process that already holds a stolen console handle can choose the client address it reports (TM-42). Without the handle a direct connection gets `403` and nothing else; the deployment keeps the listener on loopback or inside the gateway's network namespace.
- A grant created from a verified, non-authoritative email rests on the operator's confirmation of the displayed user (TM-46): Hopae cannot establish that the mailbox's current holder is the account's original person.
- WebAuthn-elevated AAL 2 sessions reach the native Human owner path only through the exact provenance record of their elevation (ADR-0017 decision 15); sessions elevated before migration 12 are refused there. AAL 3 is a presentation of a qualifying AAL 2 session, never a stored level, and can be required by step-up rules and `admin.require_aal` (TM-53). Removing a passkey keeps the acting session alive even if that passkey elevated it; the acting session has just proven a second factor. Users without a factor whose primary sign-in is older than five minutes must sign out and in again to enroll (ADR-0017 decision 10).
- Console reads are not audited, except the subject directory and authentication explain reads (`admin.read`, TM-60, TM-61), and a read-only administrator sees the same personal data as an administrator (TM-45); audit of the remaining reads and a reduced-data role are backlog items.
