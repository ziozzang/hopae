# ADR-0016: The management console is a Hopae application on its own listener, authenticated from the session handle, with administrators as granted users

- Status: Proposed
- Date: 2026-10-09
- Deciders: designer, orchestrator, maintainer
- Scenarios: 300, 301, 302, 303, 304, 305
- Threat model: TM-15 (rewritten), TM-42, TM-43, TM-44, TM-45, TM-46; new flow C
- Supersedes: none (narrows the M4 sketch in the [architecture](../ARCHITECTURE.md#data-model): the `admins` table with its own passwords is not built; amends [ADR-0010](0010-provider-abstraction.md) with the reauthentication capability, the reauthentication parameters and the `auth_time` provenance rule of decision 15, ADR-0010 stays Accepted and links here)

## Context

- M1 is live behind the reference gateway with a real provider. The maintainer wants an administration page next, before M2 and M3: list and search users, see a user's identities, sessions and recent events, disable and enable a user, end one session or every session of a user, browse the login history and audit trail with filters, and see the status of applications, providers, the store and the build. Everything else of the M4 scope (provider and application management, blacklists, OpenAPI, API tokens) stays later. This milestone is **M4-min** in the [roadmap](../ROADMAP.md#m4-min--management-console-minimum-020).
- The architecture sketched a management listener (M4) with its own `admins` table (username, Argon2id password hash, role) and the threat model's TM-15 assumed a bootstrap token from the environment. Nothing of that exists yet; the data model is free to change now and frozen migration `0002` cannot be edited (every schema change is a new migration).
- Hopae already has everything an administrator's session needs: a login flow with a real provider, server-side sessions with per-host handles, per-application timers and client binding ([ADR-0004](0004-session-model-and-cross-domain-handoff.md), [ADR-0007](0007-context-binding-policy.md)), `users.status` and `authz_version` read on every verify, the assurance level per handle and the elevation transaction that reissues handles ([ADR-0008](0008-second-factor-extension-point.md)), application-host entry points for sign-in and sign-out ([ADR-0015](0015-app-host-entry-points-and-upstream-cookie-stripping.md)), and a transactional audit outbox with `admin.*` kinds reserved ([ADR-0009](0009-event-model.md)).
- The gateway injects identity headers into upstream requests. They are trustworthy for an upstream **only** when the upstream is reachable solely through the gateway. Hopae's listeners run on the gateway host's loopback (`network_mode: host` in the reference deployment), where any local process can connect; the verify endpoint needs the caller key for that reason (HC-3, TM-14). The gateway cannot add a static header to an upstream request (HC-3 covers the external-auth call only), so a caller key for an upstream listener is not available, and a `trusted_proxies` check cannot tell the gateway from another local process on the same loopback address.
- The gateway strips the Hopae cookies from upstream requests on routes that set `strip_request_cookies` (HC-12). A route whose upstream is Hopae itself must not strip them, or the upstream cannot see the credential it would validate.
- The portal is server-rendered with askama templates, English and Korean strings in TOML, a content security policy without scripts, CSRF tokens bound to a cookie plus an `Origin` check. The project's dependency policy prefers crates already present; a JavaScript build chain is not in the tree.
- Today's sessions record `auth_time = now` at the callback and the authorize request carries no `max_age` or `prompt`; a provider with a live browser session completes a new login silently. OpenID Connect Core makes `auth_time` optional on an ordinary authentication response and required only when `max_age` was requested. **Google documents that it does not support reauthentication requests** (`prompt=login` is not among its supported values) and that `auth_time` needs a claims request and additional settings (reviewed 2026-10-09, Google Identity documentation); a generic OpenID provider honors `max_age` per the core specification. Hopae therefore cannot promise a provider-verified fresh credential for every provider; it can for providers that implement the standard parameter.
- `events` is indexed on `(at)`, `(user_id, at)` and `(client_ip, at)` without a tie-breaker; `sessions` on `(user_id, terminated_at)`; there is no index for a kind or session filter or for listing by creation time. The session row stores the user agent as a digest only. The store's migration runner applies pending migrations before it checks the pre-release version-2 guard, the startup path writes the pre-migration backup before the store is opened, and a `LIMIT` bounds results, not the rows examined. The verify engine's lifetime evaluator treats a handle or session as expired when `now ≥ min(stored deadline, created_at + the current policy's absolute)` or `now ≥ last_seen_at + idle`, with a 60-second tolerance for a future-dated `created_at`. Store reads run on the blocking pool and writes on a dedicated thread; a Tokio task-local is not visible there unless its value is passed explicitly, and rusqlite's progress handler needs its `hooks` feature.
- Second factors arrive in M5; today every session is single-factor (`aal = 1`), and `apps[].step_up` is parsed but not enforced.
- Decisions taken by the maintainer after design review pass 1 (recorded internally): a grant by a verified email stays allowed; grants are also seedable from the configuration file with provider-style `managed_by` and tombstones; peers of the admin listener outside `trusted_proxies` are handled per a configuration option whose default refuses; the viewer role sees every datum and is read-only, described as a read-only administrator. After pass 2 the orchestrator ruled that providers declare a reauthentication capability, that console freshness with a provider that lacks it is documented as Hopae login age with silent provider single sign-on as an explicit residual, and that a real administrator step-up needs Hopae's own second factor, proposed as the milestone after M4-min.

## Decision

The console and its API are **a Hopae application served by Hopae**: a third listener, a reserved application registered like any other, the ordinary login and sign-out flows through the gateway, and an administrator check that Hopae performs on every request from its own session handle. Administrators are ordinary users with a grant row.

1. **Where it runs.** A third TCP listener, `listen.admin` (default `127.0.0.1:8702`), with a router disjoint from the portal's and the gateway's ([ADR-0003](0003-http-stack-axum-on-hyper.md)). It exists only when `admin.public_url` is set (the console's externally visible origin, `https://hopae-admin.example.test` in examples); without it nothing binds and `hopae --check` prints nothing about it. It is bound to loopback like the other listeners and must not be publicly reachable except through the gateway.
2. **The console host is a registered application.** `admin.public_url` registers the implicit application `admin` (a reserved `app_id`, like `default`; an `apps[]` entry with that id is a configuration error) with `hosts = [its host]`, `ports = [its port or 443]`, `session = admin.session` (defaults `idle: 30m`, `absolute: 12h`), `binding = admin.binding` (defaults `ip: strict`, `ua: off`, `on_mismatch: terminate_session`), `on_authz_change = terminate`, `verify_cache_seconds = 0`, `logout_confirm = true`, `max_auth_age = admin.max_auth_age` (decision 15) and `step_up = [{"path_prefix": "/", "require": {"aal": admin.require_aal}}]` when `admin.require_aal` is `2`. Being an application makes the console host a credential destination the operator vouches for, puts it in the return-origin allowlist, and gives it the whole M1 machinery unchanged: the unauthenticated `302` to the portal, the browser-bound handoff to `/_hopae/login`, the host-only `__Host-hopae` handle, the `/_hopae/logout` ticket. The gateway route for the host is the contract's protected whole-host fragment with one difference: **no `strip_request_cookies`** (the upstream is Hopae and needs the handle). `hopae --check` prints that fragment; the phase-1 drift report flags a console route that strips or lacks `auth`.
3. **Every request is authenticated by Hopae from the handle, never from headers.** The admin listener reads the configured handle cookie, the client address and scheme through the `trusted_proxies` rule the portal uses, and the request's own path, builds a `VerifyInput` for the console host (`navigation: Other`, no handoff, internal caller) and runs the verify engine (`verify::decide_with_cause`, [ADR-0013](0013-gateway-adapter-boundary.md)): handle → session → timers → binding → user status and `authz_version` → application policy, freshness included → identity. Only `Decision::Allow` proceeds; a freshness refusal (`Login { kind: Reauth }`) is answered `403 auth_too_old` with the console link, and every other outcome is `403 {"error":"login_required","login":"<admin.public_url>"}` (an HTML page with that link for a document navigation); none creates anything or sets a cookie. The listener never starts a login, never redeems a handoff and never ends a session on its own initiative: the gateway's verify call for the same host already did that before the request was proxied, so a non-allow outcome at the listener means a direct connection, a misconfigured route or a session that changed between the two checks. Every denial is counted and recorded through the **same denial-observation helper the gateway listener uses** (`http::denials`), with the resolved client address, the `admin` application and the request id (review pass 1, F8). The identity headers the gateway injects (`x-forwarded-user`, `x-hopae-*`) and the gateway context headers other than the forwarding headers are **never read** (the boundary lint keeps their names out of the admin module). A request whose forwarded host is not the console host is `404`.
4. **Peers that are not the gateway (review pass 1, question 1; maintainer decision 3).** `admin.untrusted_peers` decides what the listener does with a TCP peer outside `trusted_proxies`: `refuse` (default) answers `403 {"error":"untrusted_peer"}` before reading a cookie, logs it at `warn` (rate limited) and counts it, so a deployment whose gateway is not the one talking fails loudly; `as_client` treats the peer as the client, as the portal does. Neither value authenticates the gateway: a local process on the same loopback address is indistinguishable from it, so a local process that already holds a stolen console handle can present a chosen `x-forwarded-for` and defeat IP binding. That is the explicit deployment residual of TM-42; the listener stays on loopback or inside the gateway's network namespace.
5. **Administrators are granted users.** A new table `admin_grants(user_id PRIMARY KEY REFERENCES users, role IN ('admin','viewer'), managed_by IN ('file','api'), source_email, granted_at, granted_by, revoked_at, revoked_by, note)` (migration `0003`). After the engine allows, the listener reads the grant of `identity.user_id` from the primary store on **every** request (no cache); a missing or revoked row is `403 not_admin` with the user id and email on the page so the person can hand them to an operator, and a required event `admin.denied` (`reason=not_admin`). `admin` may read and mutate; `viewer` is a **read-only administrator**: every page and every `GET`, the same data (emails, client addresses, history), no mutation (`403 role_insufficient` with `admin.denied`). There are no passwords, no separate accounts and no bootstrap token: the `admins` table of the architecture sketch is not built.
6. **A grant binds to a user id, resolved once (review pass 1, F1; maintainer decision 1).** A grant names a `user_id`. It may be *created* from an email, and that resolution happens exactly once, at grant time, against `users.primary_email` (`email_verified` required); the row records the address it was resolved from in `source_email` and is never re-resolved. An email proves control of a mailbox at the provider when the provider asserted it, not that the same person holds it later: a stale provider account can still assert a reassigned address, and a user's `primary_email` stays reserved after the provider's address changes ([ADR-0011](0011-account-linking-policy.md)). Therefore:
   - `hopae admin grant <user_id|email>` always prints the user it resolved — `user_id`, `display_name`, `created_at`, `last_login_at`, `primary_email` with its `verified` and `authoritative` flags, and every linked identity as `provider:subject` — before writing.
   - For an email that is **not authoritative** (`users.email_authoritative = 0`) the command refuses (exit `2`) unless `--confirm <user_id>` names exactly the resolved id; an authoritative email and a grant by `user_id` need no confirmation.
   - A configuration-file entry (decision 7) given by email alone is applied only when exactly one user holds that verified address **and** it is authoritative; an entry with both `user_id` and `email` is applied only when they name the same user; otherwise preflight warns and the import skips the entry.
   - Residual (TM-46): the operator remains the one who decides that the displayed user is the intended person; Hopae shows the evidence and refuses to guess.
7. **Grants are also seeded from the configuration file (maintainer decision 2; review pass 2, P2-06).** `admin.users[]` entries `{user_id?, email?, role (default admin), note?}` are imported at start and by `hopae admin import` under the [ADR-0010](0010-provider-abstraction.md) rule adapted to grants, in **one store transaction** that keeps each entry's original key (`user_id`, `email`, or both) and keeps skipped entries as *present*: first, every entry — skipped ones included — is matched against existing rows by its key: an entry with a `user_id` matches that row; an entry with an email alone matches the `managed_by = file` row whose `source_email` equals it, whichever user that row is bound to (an address is **never re-resolved** for a row that exists); second, a matched live file row has its `role` and `note` updated, unless the entry is skipped (mismatched `user_id`/`email`, or otherwise invalid), in which case the row is left untouched and the warning names the entry; third, an unmatched entry is resolved once inside the same transaction (decision 6) and inserted as `managed_by = file`, or skipped with its reason; fourth, a live file row that no entry matched is revoked (`revoked_by = file`), because removing an administrator from the file must remove the authority, while a row an entry still names — even a mismatched one — is never revoked by absence. `managed_by = api` rows (created or last changed by the CLI) and tombstones (revoked rows) are never touched by the import, so a runtime revocation survives restarts; `hopae admin import --force <user_id|email>` selects the existing row by the same key rule (an email selects the row bound through `source_email` before any resolution) and reasserts the file entry over it. `hopae admin grant` or `revoke` on a file-managed row flips it to `api`. Preflight warns when a file entry's email now resolves to a different user than the row it is bound to, when an email is ambiguous or unverified, when an entry's `user_id` and `email` disagree, and when an entry names no existing user.
8. **Bootstrap and recovery are a command.** `hopae admin grant`, `revoke`, `list` and `import` run against the store directly (like `providers import`, safe while an instance runs; the instance reads grants per request, so no restart). A user who never signed in does not exist and `grant` exits `2` with "sign in once first": the first administrator signs in through the console host (or any application), reads the user id from the `403 not_admin` page, and an operator runs `grant` (or lists the user in `admin.users[]`). Every CLI or file change writes an `admin.grant` or `admin.revoke` event with `attrs.actor` = `cli` or `file` in the same transaction as the row. Granting and revoking from the console itself is not in M4-min; the user detail page shows the grant read-only.
9. **UI: server-rendered pages, no scripts, plus a JSON API.** Pages are askama templates in English and Korean selected by `Accept-Language` (strings in the portal's TOML files under `admin.*` keys), styled by one static stylesheet, with the portal's security headers on every response (`cache-control: no-store`, `x-content-type-options: nosniff`, `referrer-policy: same-origin`, `x-frame-options: DENY`, `x-robots-tag: noindex`) and the content security policy `default-src 'none'; style-src 'self'; img-src 'self'; form-action 'self'; frame-ancestors 'none'` — no script of any origin. Forms are plain `POST`s answered by `303` to the page they came from (never a client-supplied URL). The same handlers serve JSON under `/v1/`: `GET /v1/me`, `GET /v1/users`, `GET /v1/users/{id}`, `POST /v1/users/{id}/disable`, `POST /v1/users/{id}/enable`, `POST /v1/users/{id}/sessions/terminate`, `GET /v1/sessions`, `GET /v1/sessions/{id}`, `POST /v1/sessions/{id}/terminate`, `GET /v1/events`, `GET /v1/status`. Errors are `{"error":"<code>"}`. The API is authenticated exactly like the pages; API tokens are later work.
10. **CSRF.** HTML forms carry a token issued by the portal's CSRF module with a new purpose `admin`, bound to the presented handle value, and require `Origin` equal to `admin.public_url`'s origin; a failure is `403 csrf_rejected` with a `csrf.rejected` event (`purpose=admin`, `cause=token|origin`) and no change. JSON mutations require `content-type: application/json`, the header `x-hopae-admin-request: 1`, `Origin` equal to the console origin when present, and `sec-fetch-site` equal to `same-origin` or `none` when present; no `OPTIONS` handler exists, so no preflight ever succeeds. `SameSite=Lax` on the handle is the layer beneath both.
11. **Mutations are fenced and audited in one transaction (review pass 1, F3; pass 2, P2-02).** Each mutating store method takes the actor (`user_id`, `session_id`, handle digest) and the current policy durations, and, as the first statement of its immediate write transaction, re-evaluates the actor with **the lifetime semantics of the verify engine** at that instant: the session is live, `now < min(stored absolute deadline, created_at + session.absolute)` and `now < last_seen_at + session.idle`; the handle is the actor's, for the console host, unrevoked, `now < min(stored absolute deadline, created_at + admin.session.absolute)`, `now < last_seen_at + admin.session.idle` and at least `admin.require_aal`; neither `created_at` lies more than 60 s in the future; the user is `active` and `users.authz_version` still equals the session's immutable `authz_version_at_auth` (the implicit application is `terminate`, so any authorization change invalidates); the session satisfies the freshness predicate of decision 15; the grant is live with role `admin`. Any failed predicate aborts the write with `403 actor_revoked` and no change. The change and its `admin.*` event are committed together (outbox, ADR-0009). Events name the **target** in the first-class columns (`user_id`, `session_id`) and the **actor** in `attrs.actor` (a user id, `cli` or `file`) and `attrs.actor_session`:

   | Action | State change | Events in the same transaction |
   | --- | --- | --- |
   | Disable user | `users.status = disabled`, `authz_version += 1`, every live session of the user terminated (`cred_gen += 1`, handles revoked, codes consumed) | `admin.user_disable` (attrs `actor`, `actor_session`, `count`) and one `session.terminated` (`reason=user_disabled`) per session |
   | Enable user | `users.status = active`, `authz_version += 1`; no session revived | `admin.user_enable` |
   | Terminate one session | `terminate_session(reason=admin)` | `admin.session_terminate` and `session.terminated` (`reason=admin`) |
   | Terminate every session of a user | one `terminate_session(reason=admin)` per live session | `admin.sessions_terminate` (attrs `count`) and one `session.terminated` per session |
   | Grant, revoke, import (CLI or file) | `admin_grants` row written | `admin.grant` / `admin.revoke` (attrs `actor` = `cli` or `file`, `role`, `previous_role`, `managed_by`) |
   | Denied console request | none | `admin.denied` (`reason` ∈ `not_admin`, `role_insufficient`, `auth_too_old`, `aal_insufficient`, `self_target`, `actor_revoked`; attrs `endpoint`, `method`) |

   An action that changes nothing answers `200 {"changed": false}` and writes no event. An administrator cannot disable their own user (`403 self_target`); terminating their own session is allowed and acts as a sign-out. Reads are not audited.
12. **Queries examine a bounded window and page on immutable keys (review pass 1, F4, F5, F7; pass 2, P2-03, P2-04, P2-05).** Every listing is one indexed range scan of at most **10,000 candidate rows** (the window) in the order of one index, followed by the residual filters inside that window; the page returns up to `limit` matches (1–200, default 50) and a cursor taken from the **last candidate examined** when the window was full (or from the last returned match when more matches than `limit` were found), so a page with few or no matches still advances. The window's size and its last candidate are reported **independently of the matches** (an empty match set over a full window still yields the continuation cursor). A first page and a cursor page are **separate statements**: the cursor page seeks with a composite row-value comparison on the index's trailing columns (`(at, event_id) < (:at, :id)`), so the work of a deep page is bounded by the window and independent of how many rows precede the cursor. A dense walk takes about `rows / limit` requests; a sparse one at most `rows / 10,000` more. Cursors are opaque, MAC-protected positions (`sort key`, `id`); a forged one is `400 invalid_cursor`. Sort keys are immutable: users by `(created_at, user_id)`, sessions by `(created_at, session_id)` with `last_seen_at` displayed, events by `(at, event_id)`; a keyset walk therefore neither skips nor repeats a row that existed when it started, whatever activity happens meanwhile. Migration `0003` replaces the three `events` indexes with `(at, event_id)`, `(user_id, at, event_id)`, `(client_ip, at, event_id)`, `(kind, at, event_id)` and adds `(session_id, at, event_id)`; adds `users(created_at, user_id)` and the partial indexes `sessions(created_at, session_id) WHERE terminated_at IS NULL` and `sessions(user_id, created_at, session_id) WHERE terminated_at IS NULL`; adds `sessions.bound_ua_prefix` (filled from then on), `sessions.auth_time_source` and `login_txns.reauth_max_age` (decision 15). The index predicate is chosen by a fixed priority (`session_id`, then `user_id`, then `client_ip`, then `kind`, then time only); `since`/`until`, `outcome` and the users' search terms are residual. Users: `q` (≤ 128 characters) matches `primary_email` and `username` by prefix and `display_name` by substring, within the window; filter `status`. Sessions: live rows only, filter `user_id`. The user detail returns **previews**: at most 20 live sessions (newest created first) with the live total and a link to `/sessions?user_id=…`, at most 20 recently terminated sessions, at most 50 identities, at most 50 recent events with a link to `/events?user_id=…`; a session detail returns at most 100 handles. Every console store operation — listing, search **and mutation** — runs under `admin.query_budget_ms` (default `2000`): the absolute deadline is captured before the work is dispatched and handed to the job that executes it on the blocking pool or the writer thread, which installs a SQLite progress handler scoped to that job (cleared before the connection is reused), checks the deadline between the statements of multi-statement jobs (disabling a user, terminating every session, reauthentication, the grant import), and on expiry **interrupts the statement inside SQLite**, rolls back and answers `503 store_unavailable`.
13. **Migration 0003 is applied only on a validated foundation, and nothing is backed up before that (review pass 1, F6; pass 2, P2-09).** The startup path and the CLI first open the database read-only and validate the structures its recorded version requires (version 2: the pre-release checks that exist today; version 3: those plus `admin_grants`, `sessions.bound_ua_prefix`, `sessions.auth_time_source`, `login_txns.reauth_max_age` and the new indexes); a database that fails is refused with its version unchanged **and no backup file created or replaced**. Only then is the pre-migration backup written — to a temporary name, renamed over any previous backup only after the copy succeeded — and the migration runner validates again before applying the pending migrations and once more at the final version. A pre-release version-2 database is still refused, `schema_migrations` stays at 2, no `admin_grants` table exists, and an existing `hopae.db.bak-v2` is preserved.
14. **Status is read-only.** `GET /v1/status` and the front page show: applications (id, hosts, ports, enabled, lifetimes, binding, `logout_confirm`, `max_auth_age`), providers (id, kind, display name, enabled, `managed_by`, health from the registry's cached discovery state, the reauthentication capability, the secret's environment variable **name** and whether it is set), the store (kind, schema version, counts of users, live sessions and events, pending and failed deliveries per sink), the build (version, contract version), the configuration generation and digest, `started_at`, and the `insecure_mode` and `unauthenticated_caller` flags of `/healthz`. No value of any secret is ever rendered. Runtime provider changes are not in M4-min; when they come, a `POST /v1/providers/{id}` handler sets `managed_by = api` on the row by the ADR-0010 rule and the status page's `managed_by` column is where the operator sees that the file no longer owns the row.
15. **Console freshness: a provider-verified challenge where the provider supports it, Hopae login age where it does not (review pass 1, F2; pass 2, P2-01, P2-07, P2-08; amends ADR-0010).**
   - **Capability.** Every provider declares `reauth`: `max_age` (the provider honors the OpenID Connect `max_age` parameter and returns `auth_time`) or `unsupported`. The generic `oidc` kind defaults to `max_age`; the `google` preset is `unsupported`, because Google documents that it does not support reauthentication requests. The stored provider setting `reauth` overrides the default (an operator who has verified a provider's behavior may set it either way); `hopae --check` prints each enabled provider's capability and what console freshness means with it.
   - **Provenance.** `sessions.auth_time_source` is `provider_claim` or `hopae_completion` (migration `0003`; existing rows become `hopae_completion`). At **every** OIDC callback: an `auth_time` claim that is present must be a valid integer not later than `now + 60 s`, else the login **fails** (`invalid_auth_time`, nothing created; an invalid claim is never replaced by `now`); a valid claim is stored as the session's `auth_time` with source `provider_claim`; an absent claim stores the callback time with source `hopae_completion`. `x-hopae-auth-time` reports the stored value. `session.created` and `login.succeeded` carry `attrs.auth_time_source`.
   - **One predicate.** `FRESH(session, now, N)` is defined once and used by the verify engine, the admin listener and the actor fence: `auth_time ≤ now + 60 s` **and** `now − auth_time < N` (an age equal to `N` is not fresh; the 60 s tolerate a provider clock ahead of Hopae's). For a session whose provider is `max_age`, `FRESH` additionally requires `auth_time_source = provider_claim`: a session authenticated without the claim, a legacy session, or a session the provider completed from its own single sign-on without a verified time is not fresh and is challenged on its first console entry. For a session whose provider is `unsupported`, `FRESH` is **Hopae login age**: the time since Hopae's own sign-in completed (or since the provider's claim, when it happened to send one), and nothing more.
   - **The challenge.** `admin.max_auth_age` (duration, default `12h`) is the implicit application's `max_auth_age` policy, evaluated by the verify engine on every verify for the console host after the step-up rules: when `FRESH(session, now, N)` fails, a document navigation is answered with the ordinary unauthenticated `302` to the portal whose transaction carries the **server-owned reauthentication requirement** (`login_txns.reauth_max_age = N` seconds; reason `reauth_required`), and a non-document request with `401 {"error":"reauth_required"}`. For such a transaction the portal offers no single sign-on even though a valid portal handle is present (the handle is kept) and sends the browser to the provider. With a `max_age` provider the authorize request carries `max_age=N` and, unless the stored setting `reauth_prompt` is `"none"`, `prompt=login`; at the callback the ID token **must** carry `auth_time` (missing → `login.failed` with `reauth_auth_time_missing`) and must satisfy `FRESH` with `N − 600 s` (the transaction lifetime, so that the first console verify after the handoff is fresh too; `N/2` when `N ≤ 1200 s`), else `reauth_not_fresh`; nothing is created on failure. With an `unsupported` provider the authorize request is an ordinary one (no `max_age`, no `prompt`), and the callback's completion time becomes the new `auth_time` with source `hopae_completion`: the provider may have completed silently from its own session — that is the documented residual, and operators are told to enforce a second factor at the provider for administrator accounts. On success, when the portal handle names a live session of the **same** user, the session is reauthenticated in the elevation-shaped transaction of ADR-0008: `sessions.auth_time` and `auth_time_source` updated, a factor entry `{kind: oidc, provider, at: auth_time}` appended, `cred_gen += 1`, every handle revoked (`reason=reauth`), outstanding codes consumed, the portal handle reissued and the browser handed off to the console with the new generation (`login.succeeded` with `attrs.reauth = true`); a different user or no live session makes an ordinary new session. The admin listener keeps the same predicate as a race fallback (`403 auth_too_old` with the console link); the actor fence evaluates it in SQL.
   - **What this is not.** Neither path is a second factor. A real administrator step-up is Hopae's own TOTP ([ADR-0008](0008-second-factor-extension-point.md)); the roadmap proposes pulling TOTP for administrators forward as the milestone after M4-min, with no implementation here.
16. **Limits and privacy.** `limits.admin_max_concurrent` (default `16`) refuses excess requests with `503` before any work; `admin.query_budget_ms` bounds each store operation; bodies are capped at 64 KiB, query strings at 4 KiB. Unauthenticated requests to the listener create nothing (no transaction, no required event; sampled `verify.denied` only). Client addresses and the 64-byte sanitized user-agent prefix are shown to every grant holder; the full user agent is never stored. Retention is the existing `events.retention_days` and `sessions.retention_days`; there is no export. Read-only administrators see the same personal data as administrators.

Out of scope for M4-min: managing providers, applications, blacklists or grants from the console; OpenAPI; API tokens or break-glass credentials; audit of reads; CSV export; a session's geolocation; per-page rate limits beyond the concurrency cap; `apps[].max_auth_age` for ordinary applications (the engine rule exists; the key stays scheduled); Hopae's own second factor for administrators (proposed next).

## Consequences

### Positive

- No second authentication system: no passwords, hashes, bootstrap tokens, lockout logic or account store for administrators; the console inherits every M1 guarantee (binding, lifetimes, revocation on `authz_version`, logout everywhere) and every M5 one (second factors, step-up) without changes.
- The trust boundary is the handle, not the gateway: a request that bypasses the gateway, a route without `auth`, or a forged identity header never yields an administrator; the console fails closed to `403`, and by default an unexpected peer fails loudly.
- Freshness claims match what each provider can deliver: a provider-verified `auth_time` where the provider implements `max_age`, an honestly labeled Hopae login age elsewhere; an invalid claim fails a login instead of becoming "fresh"; every session records where its authentication time came from.
- One mechanism for bootstrap, recovery and revocation (the CLI and the file against the store), taking effect without a restart; grants in version control for deployments that want them; the file can neither resurrect a runtime revocation nor revoke an entry that is still present.
- No JavaScript, no build chain, no new dependency beyond rusqlite's `hooks` feature; the portal's templates, i18n, CSRF and security headers are reused as they are.
- Every administrative change has its record in the same transaction, attributable to a user, the CLI or the file; every listing and mutation costs a bounded, interruptible amount of work; a defective database is refused before anything is written beside it.

### Negative

- The console is only reachable after the gateway's protected route for the console host exists, with the standard `auth` block and **without** `strip_request_cookies`; copying the default application fragment breaks it (the drift report and `--check` say so).
- With the reference provider (Google) console freshness is Hopae login age, not a provider-verified challenge, and a provider that single-signs-on silently satisfies it; the mitigations are the provider's own second factor for administrator accounts, the short lifetimes and strict binding of the implicit application, and Hopae's own TOTP in the proposed next milestone.
- With a `max_age` provider every legacy session and every session authenticated without an `auth_time` claim is challenged on its first console entry.
- A reauthentication revokes the session's handles on every host; other applications re-handoff silently by single sign-on, at the cost of one redirect pair each, and non-navigating requests in flight during the rotation can fail once.
- Non-browser API clients need a browser-obtained cookie until API tokens exist.
- A grant is a user id: an administrator who loses their provider account loses the console; recovery is the CLI or the file granting another user. Granting by a non-authoritative email needs a second, explicit step.
- A sparse search or filter may answer a short page and need several requests to cross a large table; the bound is the price of never scanning it whole in one request. Each page materializes its window.
- Users and sessions are listed by creation time, not by last activity; the activity column is informational.

### Neutral

- Contract: the gateway contract gains the reason code `reauth_required` on the `302` and `401` rows and one sentence about the console route; the contract version stays 1.1 (adding a reason code is a minor change).
- ADR-0010 is amended (not edited) by decision 15: the `reauth` capability and `reauth_prompt` as stored provider settings, `max_age`/`prompt` on reauthentication transactions with capable providers, and `auth_time` provenance on sessions.
- Follow-ups recorded in the roadmap: TOTP for administrators proposed as the milestone after M4-min; grants and provider management from the console (M4), API tokens (M4), read audit and export (backlog), `apps[].max_auth_age` for ordinary applications (backlog, the engine rule exists), `hopae gateway render` printing the console fragment (M2 phase 1).
- The architecture's data model replaces the `admins` sketch with `admin_grants` and lists the new columns and indexes; the threat model's TM-15 is rewritten and TM-42 to TM-46 are added with flow C.

## Alternatives considered

| Alternative | Why not |
| --- | --- |
| A path on the portal host (`https://auth.example.test/admin/`) using the portal handle | The portal is the highest-exposure origin Hopae has; administrator pages would share its origin, cookie jar and CSP with the login flow, and the portal handle carries the `default` policy (24 h idle, no per-host binding choice). A separate host gets its own `__Host-` cookie, its own route (and whatever the gateway can put in front of a route: address policy, country policy) and its own lifetimes. The maintainer also asked for a host. |
| Trust the gateway's injected identity headers at the admin listener | Trustworthy only if the listener is reachable solely through the gateway; on the reference deployment (host network) any local process can connect, and the gateway cannot add a static secret to an upstream request. A caller key for upstreams does not exist (HC-3 is auth-call only). The handle is a credential the listener can verify itself. |
| A public route (no `auth`) with the admin listener running its own login start, handoff redemption and entry points | Duplicates the gateway adapter's rendering of `Login`, `Handoff`, `Switch` and the entry points for one host, with a second set of transaction-creating paths exposed to the internet; the protected route gives all of it for free and the listener only confirms. |
| Separate administrator accounts with passwords (the M4 sketch; the gateway's model) | A second credential system with its own bootstrap token, hashing, lockout, reset and lockout-recovery story, weaker than the provider login it would sit next to (no second factor at all); the project would audit two login paths. |
| Grants only in the configuration file, or only in the table | The file alone cannot revoke without a restart; the table alone cannot be version-controlled. The provider import rule already reconciles both with one writer per row (`managed_by`), so it is reused; removal from the file revokes because an administrator list must be subtractive, unlike a provider list. |
| Require `email_authoritative` for every grant by email | The maintainer wants verified addresses usable; authority at the provider still does not prove human continuity after a mailbox is reassigned. The printed resolution, the confirmation flag for non-authoritative addresses, the one-time binding and the file-entry rule close the wrong-principal path without forbidding the common case. |
| Authorization by group membership (`users.groups` contains `hopae-admins`) | Groups come from providers or policy in M2+ and are not operator-managed today; a grant row is explicit, attributable and revocable on its own. Groups can map to grants later. |
| Static SPA plus JSON API | Needs a build chain or vendored scripts, a `script-src` in the CSP, a second i18n mechanism and a CSRF token round trip; the pages needed are tables and confirmation forms, which the portal's server-rendered pattern already does. The JSON API exists anyway for scripts. |
| `max_auth_age` as a Hopae login-age check for every provider (the pass-1 design) | For providers that implement `max_age` it would forgo a verifiable challenge the standard offers (review pass 1, F2). Where the provider cannot deliver one, login age is exactly what is claimed now, labeled as such. |
| Treat Google as a `max_age` provider (the pass-1 revision) | Google documents that it does not support reauthentication requests and that `auth_time` needs a claims request and extra settings (review pass 2, P2-07); promising a Google re-login page would be a promise Hopae cannot keep. The capability flag makes the claim per provider. |
| Store `now` when an `auth_time` claim is absent or invalid, without recording provenance (the pass-1 revision) | Launders an absent or invalid claim into freshness (review pass 2, P2-01): a session that the provider completed silently looked freshly authenticated. Provenance is now a column, an invalid claim fails the login, and a `max_age` provider's console session must carry a provider claim. |
| Different freshness allowances at the callback and at verify (the pass-1 revision: `N + 60 s` versus `N`) | A permitted callback produced a session that the next verify immediately challenged again (review pass 2, P2-08). One predicate, one tolerance, and a callback headroom of the transaction lifetime make a successful reauthentication reach the console. |
| Unconditional reauthentication on every first console entry | Punishes a session that authenticated minutes ago on another host and still leaves aging sessions to the age rule; evaluating the age rule at every console verify covers first entry and later aging with one mechanism and one bound. |
| Password or TOTP re-prompt at the console for step-up, built here | A second factor is M5 (`Factor` trait); building a one-off here would be a parallel path. It is proposed as the next milestone instead, with the `Factor` trait. |
| Activity-ordered session listing (`last_seen_at`) with keyset cursors | A row whose sort key moves past the cursor between two pages is skipped forever (review pass 1, F7); keyset pagination needs immutable keys, so creation order is used and activity is displayed. |
| `LIMIT` as the scan bound; a nullable cursor predicate in one statement; window metadata projected onto matches | A `LIMIT` bounds rows returned, not rows examined (pass 1, F4); a nullable cursor predicate defeats the index seek so deep pages re-walk every preceding entry (pass 2, P2-04); metadata on match rows vanishes when nothing matches (pass 2, P2-03). Separate first-page and cursor-page statements with a row-value seek, and metadata reported from the materialized window, fix all three. |
| A Tokio task-local deadline read from inside the SQLite callback | Blocking-pool and writer-thread code does not see the caller's task-local (pass 2, P2-05); the deadline is captured before dispatch and handed to the job. |
| Back up before validating (the current startup order) | A refused pre-release database would still get a backup written (and an older backup deleted) before the refusal (pass 2, P2-09); validation now precedes any backup, and a backup replaces its predecessor only after it was written. |
| Audit every read | Floods the event table with one row per page view, under the same retention as security events; reads are bounded to grant holders and left unaudited in M4-min, recorded as a residual. |
| Disable only changes status and lets `on_authz_change` decide about sessions | A `refresh` application would keep the disabled user's sessions listed as live until their next verify denies them; terminating them with the status change keeps the session list truthful and makes re-enable require a fresh login. |

| Pass | Date | S1 | S2 | S3 | S4 | Outcome |

Findings and dispositions (the reports are recorded internally):

- Pass 1 — F1 (S1): a grant by email could name the wrong principal. FIX_FIRST: decision 6 (one-time binding, printed resolution, `--confirm`, the file-entry rule, TM-46). F2 (S2): `max_auth_age` promised freshness a silent provider login could satisfy. FIX_FIRST: decision 15 (revised again in pass 2). F3 (S2): the actor fence accepted an expired or authorization-stale actor. FIX_FIRST: decision 11. F4 (S2): `LIMIT` did not bound rows examined. FIX_FIRST: decision 12. F5 (S2): the user detail escaped the pagination bound. FIX_FIRST: previews (decision 12). F6 (S2): migration 0003 would bypass the pre-release guard. FIX_FIRST: decision 13. F7 (S2): activity-ordered keyset pagination skipped live sessions. FIX_FIRST: creation-time ordering. F8 (S3): direct-listener denials were not recorded. FIX: the shared denial helper (decision 3).
- Pass 2 — P2-01 (S1): an ordinary login without an `auth_time` claim was stamped `now` and satisfied the console; a future-dated claim was replaced by `now`. FIX_FIRST: `auth_time_source` on sessions, an invalid claim fails the login, a `max_age` provider's console session must carry a provider claim, legacy sessions are challenged (decision 15; scenario 300 (6, 15, 16, A9)).
- P2-02 (S2): the fence ignored the effective absolute deadline `created_at + current policy.absolute`. FIX_FIRST: the fence takes the policy durations and uses the engine's lifetime semantics (decision 11; scenario 300-A3 variants 11–12).
- P2-03 (S2): a window whose candidates all failed the residual filters returned no metadata and lost the continuation. FIX_FIRST: the window is materialized and its size and last candidate are reported independently of the matches (decision 12; scenario 303-3, 303-A4).
- P2-04 (S2): the nullable cursor predicate under `INDEXED BY` was not a bounded range seek; deep pages re-walked preceding index entries. FIX_FIRST: separate first-page and cursor-page statements with a composite row-value seek; deep-cursor VM-work tests independent of table size (decision 12; scenario 303-A4).
- P2-05 (S2): the SQLite progress handler could not see a Tokio task-local on the blocking pool or the writer thread, and long writes were not covered. FIX_FIRST: the deadline is captured before dispatch and passed to each job, the handler is scoped per job and cleared, multi-statement writes check between statements, and disable, terminate-all, reauthentication and import are covered; rusqlite's `hooks` feature is enabled (decision 12; scenarios 301-A4, 302-A4, 303-A7).
- P2-06 (S2): the frozen seed interface lost each entry's original key and the presence of skipped entries, so an email-only entry could re-bind to a new mailbox holder and a mismatched-but-present entry could be revoked by absence. FIX_FIRST: entries keep their key, matching precedes resolution inside the import transaction, skipped entries count as present, `--force` selects the existing binding (decision 7; scenario 305 (8, A4, A6)).
- P2-07 (S2): the Google reauthentication premise contradicted Google's documentation. FIX_FIRST by ruling: the per-provider `reauth` capability, the `google` preset `unsupported`, console freshness with such a provider documented as Hopae login age with silent provider single sign-on as the residual, preflight and the live procedure corrected, TOTP for administrators proposed next (decision 15).
- P2-08 (S2): the callback allowed `N + 60 s` while verify allowed `N`, so an accepted reauthentication could be challenged again at once. FIX_FIRST: one `FRESH` predicate with one tolerance and explicit equality semantics, a callback headroom of the transaction lifetime, boundary tests and the return-to-console test (decision 15; scenario 300 (6, A10)).
- P2-09 (S2): the startup path wrote the pre-migration backup before the foundation was validated and deleted an older backup first. FIX_FIRST: validation precedes any backup, the backup is written to a temporary name and renamed over its predecessor only on success (decision 13; scenario 305-9).
- Corrections: a dense walk takes about `rows / limit` pages (decision 12; scenario 303-3); the listener maps the engine's `Reauth` outcome to `auth_too_old` before `login_required` (decision 3; scenario 300-15).
- Reviewer recommendations on the pass-1 questions: accepted as decisions 4 (peer policy, residual kept explicit), 5 (read-only administrator wording) and 6 (confirmed user ids for non-authoritative addresses). Handle rotation on reauthentication (`reason=reauth`) without terminating the shared session is confirmed as intended.
