# 위협 모델

<!-- translation-status: source=../THREAT_MODEL.md source-rev=25 status=current -->

[문서 목차](README.md) · [English](../THREAT_MODEL.md)

이 문서는 Hopae의 살아 있는 위협 모델 버전 0입니다. 자산, 행위자, 진입점,
[아키텍처](ARCHITECTURE.md#요청-흐름)의 각 요청 흐름에 대한 STRIDE 검토, 그리고
설계가 의존하는 완화책을 담습니다. 보안 관련 변경은 모두 같은 변경에서 이
페이지를 갱신합니다. 위협 식별자(`TM-nn`)는 안정적이며 시나리오와 ADR에서
참조합니다.

## 자산

| 자산 | 위치 | 유출 시 결과 |
| --- | --- | --- |
| 세션 핸들(쿠키 값)과 포털 트랜잭션 | 브라우저 쿠키. 저장소에는 다이제스트로 보관 | 한 호스트에서의 사칭(핸들) 또는 다른 사람의 로그인 완료(트랜잭션) |
| 핸드오프 코드 | 60초 이하 동안 URL에 존재. 저장소에는 다이제스트로 보관 | 재사용이 가능하다면 대상 호스트에서의 사칭 |
| 신원 헤더 | 게이트웨이 → 업스트림 구간에만 존재 | 위조된 헤더를 신뢰하는 애플리케이션은 완전히 침해됨 |
| 제공자 자격 증명(클라이언트 비밀), SMTP 자격 증명, 웹훅 비밀, 호출자 키 | 실행 시 환경 변수 | 제공자에 대한 Hopae 사칭. 위조된 웹훅 |
| 사용자 디렉터리와 로그인 기록(개인정보) | 기본 저장소 | 프라이버시 침해. 계정 연결을 통한 계정 탈취 |
| 정책(애플리케이션, 바인딩, 차단, 단계 상승) | 기본 저장소와 설정 | 접근 제어가 조용히 완화됨 |
| 릴리스 서명 시드와 업데이트 매니페스트(M6) | 유지관리자가 오프라인으로 보관 | 모든 인스턴스의 공급망 침해 |
| verify의 가용성 | Hopae 프로세스, 저장소 | 보호된 모든 애플리케이션에 접근 불가(거부 처리) |

## 행위자

| 행위자 | 능력 | 가정하지 않는 것 |
| --- | --- | --- |
| 익명 인터넷 클라이언트 | 게이트웨이의 공개 리스너로 보내는 임의의 HTTP 요청. 다수의 IP. 임의로 고른 `Host`, 쿠키, 헤더, 쿼리 문자열 | TLS 해독. 다른 사용자의 브라우저 읽기 |
| 인증된 사용자 | 유효한 세션. 다른 출처(origin)의 악성 페이지가 스크립트로 조작할 수 있는 브라우저 | 게이트웨이 네트워크 접근 |
| 악성 형제 사이트 | 애플리케이션과 같은 등록 도메인의 형제 서브도메인 호스트 장악 | 애플리케이션 호스트 자체의 장악 |
| 침해된 애플리케이션 | 업스트림 하나와 그 응답의 완전한 통제 | Hopae의 리스너나 저장소 접근 |
| 게이트웨이와 Hopae 사이의 네트워크 공격자 | 사설 네트워크가 잘못 구성된 경우에만 해당. 설계는 범위 밖으로 다루되 HC-3으로 피해를 제한함 | — |
| 악성 또는 혼동된 ID 제공자 | 임의의 클레임 반환, 클라이언트 혼동, 느리거나 다운됨 | 다른 제공자의 서명 위조 |
| 콘솔 부여를 가진 관리자 또는 viewer(M4-min) | 모든 콘솔 작업: 사용자 비활성화, 세션 종료, 모든 사용자의 이메일·클라이언트 주소·기록 열람. 침해된 관리자 세션은 부여나 세션이 취소될 때까지 관리자로 행동함 | 두 번째 자격 증명 체계. 자체 저장소. Hopae 밖에서의 저장소 접근 |
| Lua 스크립트 작성자(M5) | 샌드박스 안에서의 임의 스크립트 | 프로세스 샌드박스 탈출 |
| 공급망 | 악성 크레이트 업데이트, 악성 릴리스 자산 | 서명 시드 보유 |

## 진입점

| 진입점 | 리스너 | 접근 주체 | 비고 |
| --- | --- | --- | --- |
| `GET /_hopae/verify` | 게이트웨이 리스너 | 게이트웨이의 네트워크 네임스페이스에 있는 어떤 프로세스든 연결할 수 있음. 호출자 키(HC-3)를 제시하는 호출자만 응답을 받음 | 가장 높은 요청 빈도. 보호된 모든 요청 |
| 보호된 모든 애플리케이션 호스트의 `GET /_hopae/login`, `GET /_hopae/logout` | 보호 라우트의 verify 호출을 거친 게이트웨이 리스너 | 인터넷. 애플리케이션 호스트의 문서 탐색으로 | Hopae가 중계되는 `302`나 `403`으로 답하며 절대 `2xx`가 아님. `/_hopae/` 이름 공간 전체가 예약되어 업스트림에 절대 도달하지 않음([ADR-0015](../adr/0015-app-host-entry-points-and-upstream-cookie-stripping.md)) |
| `GET /login`, `POST /login/<p>`, `GET /callback/<p>`, `GET/POST /logout[?txn=]`, `GET /stepup*` | 포털 라우트를 통한 포털 리스너 | 인터넷 | 브라우저 입력만 |
| `GET/POST /security*`, `POST /stepup/webauthn`, `GET /assets/webauthn.js`([WebAuthn 패스키](WEBAUTHN.md)) | 포털 라우트를 거친 포털 리스너 | 인터넷. `webauthn`이 설정된 경우에만(그 외 `404`) | 살아 있는 포털 세션 필요. 모든 POST에 CSRF와 정확한 `Origin`. 의식 상태는 서버 측·1회용. 스크립트를 실행하는 유일한 포털 페이지 |
| `GET /healthz` | 포털 리스너 | 게이트웨이를 통한 인터넷 | 비밀 정보 없음 |
| 콘솔 페이지와 `/v1/*` API(M4-min) | 관리 리스너(`listen.admin`) | 콘솔 호스트의 게이트웨이 보호 라우트를 통한 인터넷. 리스너에 도달할 수 있는 모든 프로세스 | Hopae가 모든 요청을 자신의 세션 핸들과 부여 테이블로 인증. 주입된 신원 헤더는 절대 읽지 않음. CSRF와 출처 검사. 역할([관리](ADMIN.md)) |
| 아웃바운드: 제공자 디스커버리, JWKS, 토큰, 사용자 정보. SMTP. 웹훅 | Hopae → 인터넷 | — | SSRF와 응답 크기 제어 |
| 저장소 연결 | Hopae → SQLite 파일, PostgreSQL, Redis | — | 사설 네트워크. 원격 Redis/PostgreSQL에는 TLS |
| 설정 파일과 환경 | 프로세스 시작, 다시 로드(M6) | 운영자 | 검증됨. 비밀 정보는 참조로만 |
| 업데이트 매니페스트와 자산(M6) | Hopae → GitHub 릴리스 | — | 서명된 봉투 |

## 위협 목록

심각도는 프로세스의 척도를 따릅니다(S1 보안 경계 우회 … S4 외관상 문제).
"시나리오"는 해당 위협을 검증하는 시나리오를 가리킵니다.

| ID | 위협 | 흐름 | STRIDE | 의존하는 완화책 | 시나리오 |
| --- | --- | --- | --- | --- | --- |
| TM-01 | 돌아갈 URL을 통한 오픈 리디렉션: 공격자가 돌아갈 대상이 외부 사이트를 가리키는 로그인 링크를 만듦 | 1, 3, 4 | Tampering(변조), Spoofing(위장) | 포털은 클라이언트에서 돌아갈 URL을 절대 읽지 않습니다. 대상은 verify 호출에서 게이트웨이가 만든 `x-original-url`에서 가져와 트랜잭션에 저장하고, 검증(절대 URL, 허용된 스킴, 등록되었거나 기본 허용된 호스트, 2 KiB 이하, userinfo 없음, fragment 없음)한 뒤 그 호스트로 보내는 `Location`으로만 내보냅니다. 핸드오프 `302`는 게이트웨이가 보고한 URL에서 매개변수만 뺀 정확한 URL을 대상으로 합니다. 애플리케이션 호스트 진입점은 요청 자신의 등록 출처에 대해서만 `return`을 받으며, 대상은 URL이 아니라 트랜잭션(로그아웃 티켓) 안에 담겨 포털에 도달합니다. | 005, 015 |
| TM-02 | 쿠키 토싱: 형제 서브도메인이 설정한 쿠키를 애플리케이션 호스트가 자기 세션으로 제시함 | 4, 5 | Spoofing | `__Host-` 접두사: 브라우저는 `Domain` 속성이 있는 그런 쿠키를 거부하고, 형제의 호스트 전용 쿠키를 절대 보내지 않습니다. 알 수 없는 핸들은 채택하지 않으며, 핸들은 핸드오프 시 서버 측에서만 발급합니다. 접두사가 없는 개발 모드는 안전하지 않다고 문서화합니다. | 009 |
| TM-03 | 로그인, 전환, 로그아웃의 CSRF: 악성 페이지가 공격자 계정으로 로그인을 시작하거나(로그인 CSRF), 계정을 전환하거나, 피해자를 로그아웃시킴 | 2, 3, 6 | Spoofing, Tampering | `POST /login/<p>`, `POST /switch`, `POST /logout`은 `__Host-hopae_portal` 또는 `__Host-hopae` 쿠키에 바인딩된 CSRF 토큰과 포털 출처와 같은 `Origin`을 요구합니다. 콜백은 `state`로 트랜잭션을 찾고 브라우저의 포털 바인딩 쿠키가 트랜잭션이 첫 방문 때 기록한 다이제스트와 일치해야 하므로 피해자가 공격자의 트랜잭션을 완료하게 만들 수 없습니다. `GET /logout`과 `GET /switch`는 폼만 렌더링합니다. 애플리케이션 호스트의 `GET /_hopae/logout`은 로그아웃 티켓만 만들고 그 폼으로 리디렉션합니다. 쿠키를 지우지도 아무것도 취소하지도 않으며, 문서가 아닌 요청에는 `set-cookie` 없는 `403`으로 답하고, 선택적인 무확인 모드는 브라우저가 전체 리디렉션 체인에 대해 계산하는 금지 헤더인 `sec-fetch-site: same-origin`에만 동작합니다. `SameSite=Lax` 쿠키. | 002, 006, 015 |
| TM-04 | 세션 고정: 공격자가 로그인 전에 피해자의 브라우저에 알려진 핸들이나 트랜잭션을 고정함 | 2, 3, 4 | Spoofing | 핸들은 핸드오프 시 Hopae만 생성하고 다이제스트로 저장합니다. 클라이언트가 제시한 알 수 없는 핸들은 무시합니다. 트랜잭션 쿠키는 `/login`에서 교체되고 완료 시 지워집니다. 새 세션은 모든 호스트에서 새 핸들을 받고, 포털 핸들은 로그인 시 재발급됩니다. | 002, 003 |
| TM-05 | 핸드오프 코드의 재사용 또는 탈취(방문 기록, 로그, Referer, 어깨너머 엿보기) | 4 | Spoofing, Repudiation(부인) | 원자적 조건부 소비로 1회만 사용. 60초 수명. 대상 호스트, 경로, 클라이언트 IP, 그리고 로그인을 시작할 때 그 호스트에 심은 브라우저 바인딩 쿠키에 바인딩. 발급 시점의 인증 수준과 세션의 자격 증명 세대를 기록. 문서 탐색으로만 소비. 게이트웨이를 통해서만 소비(게이트웨이는 중계하는 `302`에 `referrer-policy: no-referrer`를 설정). 거부 시 코드를 소각하고 `handoff.rejected`를 내보내며 IP별 제한(M2)에 집계. 코드는 업스트림에 절대 도달하지 않습니다. | 003 |
| TM-06 | 신원 헤더 위장: 클라이언트가 `x-forwarded-user`나 게이트웨이 맥락 헤더를 보냄 | 5 | Spoofing | 게이트웨이는 선언된 모든 신원 헤더 이름을 모든 수신 요청에서 제거하고 `x-forwarded-*`/`x-original-*`를 다시 생성합니다. Hopae의 게이트웨이 리스너는 클라이언트가 접근할 수 없고, 포털 리스너는 신뢰하지 않는 프록시의 `x-forwarded-*`를 무시합니다. 시나리오 007이 위장된 헤더가 업스트림에 절대 도달하지 않음을 증명합니다. | 007 |
| TM-07 | verify 엔드포인트의 서비스 거부: 무작위 핸들이나 긴 쿠키의 홍수. 느린 저장소 | 5 | Denial of service(서비스 거부) | verify는 제공자를 호출하지 않고 인덱스 조회 하나만 수행합니다. 쿠키 헤더는 8 KiB 이하이고 해시 전에 핸들 형식을 검사합니다. 알 수 없는 핸들에 대한 제한된 부정 캐시. 게이트웨이 리스너의 동시성 제한을 넘으면 `503`(거부 처리, 집계). 저장소 타임아웃. 게이트웨이의 `timeout_ms`가 클라이언트의 대기를 제한. 게이트웨이의 속도 제한과 실패 차단을 바깥 계층으로 사용. | 004 |
| TM-08 | 제공자 혼동: 제공자 A의 콜백이 제공자 B의 산출물로 완료되거나, 토큰 엔드포인트를 공격자 데이터에서 고름 | 3 | Spoofing, Elevation(권한 상승) | 각 트랜잭션은 선택한 제공자를 기록합니다. 콜백 경로는 제공자를 명시하고 일치해야 합니다. `state`는 (트랜잭션, 제공자)에 바인딩됩니다. 엔드포인트는 제공자 자체 설정 또는 설정된 발급자에서 가져온 디스커버리 문서에서만 옵니다. ## 잔여 위험과 열린 질문

- 침해된 애플리케이션은 자기 사용자의 신원 헤더와 `x-hopae-session`을 읽을 수 있지만 세션을 만들 수는 없습니다. 검토자는 이 식별자만으로 탈취하는 경로를 찾지 못했습니다. 애플리케이션별로 해시해야 하는지는 열린 과제로 남아 있습니다.
- strict IP 바인딩은 네트워크가 바뀐 모바일 사용자의 세션을 종료합니다. 기본값은 지시에 따라 strict이며, 운영자는 애플리케이션별로 완화할 수 있습니다. 위협 모델은 완화를 결함이 아니라 수용된 위험으로 다룹니다. 공유 NAT에서는 IP가 브라우저의 신원이 될 수 없으므로 핸드오프를 브라우저 쿠키에 바인딩합니다.
- 핸드오프 코드는 수명 동안 게이트웨이의 접근 로그에 나타납니다. 로그는 운영자의 자산이고 코드는 1회용이며 바인딩 쿠키 없이는 쓸모가 없습니다.
- 브라우저가 보낸 `x-original-*` 헤더는 수정하지 않은 게이트웨이에서 포털에 그대로 도달합니다. 포털은 이를 절대 읽지 않습니다(HC-9가 이를 제거할 것입니다).
- 탈취된 쿠키를 가진 공격자는 `terminate_session`에서 다른 IP로 그 쿠키를 제시하여 로그인당 한 번 피해자를 로그아웃시킬 수 있습니다. strict 기본값의 수용된 비용입니다.
- 운영자가 DNS를 방치한 등록 호스트는 열린 자격 증명 목적지입니다(TM-30). 불일치 검사와 선택적인 첫 핸드오프 확인은 이 운영자의 의무를 줄이지만 없애지는 못합니다.
- 이벤트 전달은 최소 1회입니다. 충돌 후 로그 한 줄이나 웹훅이 반복될 수 있으며 수신자는 `event_id`로 중복을 제거합니다.
- 제공자 삭제 툼스톤(TM-34)은 API로 관리된 ID를 데이터베이스 수명 동안 예약합니다. 그 ID를 다시 쓰려면 `--force`가 필요합니다.
- HC-12가 없으면 바인딩 쿠키와 세션 핸들이 인증된 모든 요청의 일반 `cookie` 헤더로 애플리케이션 호스트에 전송되며(TM-40), 그 호스트의 스크립트는 없는 바인딩 쿠키를 미리 심을 수 있습니다. 둘 다 같은 호스트 안의 신뢰 문제이지 호스트 간 권한 상승이 아닙니다. HC-12가 있으면 `strip_request_cookies`를 설정한 모든 라우트의 업스트림에 두 쿠키 모두 도달하지 않으며(이 필드는 라우트 수준이라 `Path=/` 쿠키를 똑같이 받는 경로 범위 호스트의 공개 라우트에도 설정해야 함), 미리 심기만 남습니다.
- `apps[].logout_confirm = false`에서 자신의 `/_hopae/logout` 링크를 프리렌더하는(추측 규칙) 애플리케이션은 마우스를 올리는 것만으로 사용자를 로그아웃시킵니다. 프리렌더는 같은 출처의 문서 탐색이고 `sec-purpose`는 전달되는 헤더에 없기 때문입니다. 기본값은 확인을 유지하며, `sec-purpose` 전달은 백로그 항목입니다.
- 확인된 로그아웃 뒤 포털은 "다시 로그인" 링크가 있는 로그아웃 완료 페이지를 보여 주며 보호된 대상으로 리디렉션하지 않으므로, 조용히 재인증하는 제공자가 클릭 없이 사용자를 다시 로그인시킬 수 없습니다.
- `apps[].logout_confirm = false`는 애플리케이션 자신의 출처를 신뢰합니다(TM-41). 애플리케이션 안의 같은 출처 탐색 가젯(자신의 쿼리에서 가져온 URL을 `location`에 대입하는 페이지, 예: `/continue?next=/_hopae/logout`)은 클릭 없이 사용자의 세션을 끝냅니다. 애플리케이션 출처의 로드된 문서가 시작한 탐색은 `sec-fetch-site: same-origin`을 제시하기 때문입니다. 이 모드는 옵트인이며 설정한 애플리케이션마다 `hopae --check`가 경고합니다.
- 로그아웃 티켓은 넘길 수 있는 취소 권한입니다. 아무도 열지 않은 티켓은 다른 사람에게 줄 수 있고, 그 사람의 첫 포털 방문이 티켓을 그 사람의 브라우저에 묶으며, 그 사람의 확인은 티켓이 가리키는 세션(만든 사람의 세션)과 자신의 포털 세션을 끝냅니다. 접근을 줄이기만 합니다(시나리오 015-A9).
- 모든 핸드오프가 `/_hopae/login`으로 전달되므로, 경로 범위 호스트는 진입점뿐 아니라 로그인이 완료되려면 `site-hopae` 라우트가 필요합니다.
- 경로 범위 호스트에서 `/_hopae` 라우트는 다른 접두사와 마찬가지로 TM-39의 대상입니다. HC-10 전까지 `/_HOPAE/logout` 같은 대소문자 변형은 공개 라우트로 넘어가 업스트림에 도달하며, 그곳에서는 진입점이 아니라 평범한 `404`입니다.
- 살아 있는 핸드오프 코드를 아는 사람은 잘못된 바인딩과 함께 제출해 코드를 태울 수 있으며, 정당한 브라우저는 복구 왕복을 한 번 더 치릅니다. 세션과 기존 쿠키는 영향을 받지 않습니다(가용성에만 해당).

- 경로 범위 보호는 게이트웨이의 라우트 선택만큼만 안전합니다. HC-10 전까지 접두사 라우트 뒤의 대소문자를 구분하지 않는 업스트림은 Hopae가 볼 수 없는 대소문자 변형(TM-39)에 노출되므로, 호스트 전체 보호가 안전한 기본값입니다.
- Hopae에 자체 2차 인증 요소가 생기기 전까지 콘솔 세션은 단일 요소입니다(TM-43). 피싱되거나 재사용된 제공자 로그인은 곧 관리자 로그인입니다. 문서화된 완화책은 관리자 계정에 제공자가 강제하는 2차 인증, `admin.max_auth_age` 뒤의 신선도 규칙(`max_age` 제공자에서는 제공자가 검증한 재인증, Google 같은 `unsupported` 제공자에서는 **Hopae 로그인 경과 시간뿐**이며 제공자가 자신의 세션으로 새 로그인을 조용히 끝낼 수 있음), 암묵적 애플리케이션의 짧은 수명과 strict 바인딩, 명령줄이나 파일을 통한 취소입니다. 최근에 다른 호스트에서 인증한 세션은 새 도전 없이 단일 로그인으로 콘솔에 들어가며, 도전을 일으키는 것은 진입이 아니라 한도입니다. 관리자용 TOTP는 M4-min 다음 마일스톤으로 제안합니다.
- 관리 리스너는 게이트웨이를 인증할 수 없습니다(정적 업스트림 헤더가 없고 로컬 프로세스가 루프백 주소를 공유함). `admin.untrusted_peers = refuse`는 예상 밖의 피어를 요란하게 실패시키지만 게이트웨이 자신의 주소를 쓰는 로컬 프로세스와 게이트웨이를 구별하지 못하므로, 이미 탈취한 콘솔 핸들을 가진 로컬 프로세스는 자신이 보고하는 클라이언트 주소를 고를 수 있습니다(TM-42). 핸들이 없으면 직접 연결은 `403` 외에 아무것도 얻지 못하며, 배포는 리스너를 루프백이나 게이트웨이의 네트워크 네임스페이스 안에 둡니다.
- 검증되었지만 권위적이지 않은 이메일로 만든 부여는 표시된 사용자에 대한 운영자의 확인에 기댑니다(TM-46). Hopae는 메일함의 현재 보유자가 계정의 원래 사람임을 확립할 수 없습니다.
- WebAuthn으로 상승한 AAL 2 세션은 상승 시점의 정확한 출처 기록을 통해서만 네이티브 Human 소유자 경로에 들어갑니다(ADR-0017 결정 15). 마이그레이션 12 이전에 상승한 세션은 그 경로에서 거부됩니다. AAL 3은 자격을 갖춘 AAL 2 세션의 표시이며 저장 수준이 아니고, 단계 상승 규칙과 `admin.require_aal`로 요구할 수 있습니다(TM-53). 패스키를 삭제해도, 그 패스키로 상승했더라도 실행 중인 세션은 유지됩니다. 그 세션은 방금 2차 요소를 증명했기 때문입니다. 요소가 없고 1차 로그인이 5분보다 오래된 사용자는 등록하려면 로그아웃 후 다시 로그인해야 합니다(ADR-0017 결정 10).
- 콘솔 읽기는 주체 디렉터리와 인증 설명 읽기(`admin.read`, TM-60, TM-61)를 빼고는 감사하지 않으며, 읽기 전용 관리자는 관리자와 같은 개인 정보를 봅니다(TM-45). 나머지 읽기의 감사와 축소된 데이터 역할은 백로그 항목입니다.
