# 위협 모델

<!-- translation-status: source=../THREAT_MODEL.md source-rev=1 status=current -->

[문서 목차](README.md) · [English](../THREAT_MODEL.md)

이 문서는 Hopae의 살아 있는 위협 모델 버전 0입니다. 자산, 행위자, 진입점,
[아키텍처](ARCHITECTURE.md#요청-흐름)의 각 요청 흐름에 대한 STRIDE 검토, 그리고
설계가 의존하는 완화책을 담습니다. 보안 관련 변경은 모두 같은 변경에서 이
페이지를 갱신합니다. 위협 식별자(`TM-nn`)는 안정적이며 시나리오와 ADR에서
참조합니다.

## 자산

| 자산 | 위치 | 유출 시 결과 |
| --- | --- | --- |
| 세션 핸들(쿠키 값)과 포털 트랜잭션 | 브라우저 쿠키. 저장소에는 다이제스트로 보관 | 한 호스트에서의 사칭(핸들) 또는 다른 사람의 로그인 완료(트랜잭션) |
| 핸드오프 코드 | 60초 이하 동안 URL에 존재. 저장소에는 다이제스트로 보관 | 재사용이 가능하다면 대상 호스트에서의 사칭 |
| 신원 헤더 | 게이트웨이 → 업스트림 구간에만 존재 | 위조된 헤더를 신뢰하는 애플리케이션은 완전히 침해됨 |
| 제공자 자격 증명(클라이언트 비밀), SMTP 자격 증명, 웹훅 비밀, 호출자 키 | 실행 시 환경 변수 | 제공자에 대한 Hopae 사칭. 위조된 웹훅 |
| 사용자 디렉터리와 로그인 기록(개인정보) | 기본 저장소 | 프라이버시 침해. 계정 연결을 통한 계정 탈취 |
| 정책(애플리케이션, 바인딩, 차단, 단계 상승) | 기본 저장소와 설정 | 접근 제어가 조용히 완화됨 |
| 릴리스 서명 시드와 업데이트 매니페스트(M6) | 유지관리자가 오프라인으로 보관 | 모든 인스턴스의 공급망 침해 |
| verify의 가용성 | Hopae 프로세스, 저장소 | 보호된 모든 애플리케이션에 접근 불가(거부 처리) |

## 행위자

| 행위자 | 능력 | 가정하지 않는 것 |
| --- | --- | --- |
| 익명 인터넷 클라이언트 | 게이트웨이의 공개 리스너로 보내는 임의의 HTTP 요청. 다수의 IP. 임의로 고른 `Host`, 쿠키, 헤더, 쿼리 문자열 | TLS 해독. 다른 사용자의 브라우저 읽기 |
| 인증된 사용자 | 유효한 세션. 다른 출처(origin)의 악성 페이지가 스크립트로 조작할 수 있는 브라우저 | 게이트웨이 네트워크 접근 |
| 악성 형제 사이트 | 애플리케이션과 같은 등록 도메인의 형제 서브도메인 호스트 장악 | 애플리케이션 호스트 자체의 장악 |
| 침해된 애플리케이션 | 업스트림 하나와 그 응답의 완전한 통제 | Hopae의 리스너나 저장소 접근 |
| 게이트웨이와 Hopae 사이의 네트워크 공격자 | 사설 네트워크가 잘못 구성된 경우에만 해당. 설계는 범위 밖으로 다루되 HC-3으로 피해를 제한함 | — |
| 악성 또는 혼동된 ID 제공자 | 임의의 클레임 반환, 클라이언트 혼동, 느리거나 다운됨 | 다른 제공자의 서명 위조 |
| 콘솔 접근 권한이 있는 관리자(M4) | 정책 완화를 포함한 모든 관리 작업 | — |
| Lua 스크립트 작성자(M5) | 샌드박스 안에서의 임의 스크립트 | 프로세스 샌드박스 탈출 |
| 공급망 | 악성 크레이트 업데이트, 악성 릴리스 자산 | 서명 시드 보유 |

## 진입점

| 진입점 | 리스너 | 접근 주체 | 비고 |
| --- | --- | --- | --- |
| `GET /_hopae/verify` | 게이트웨이 리스너 | 게이트웨이만(네트워크). HC-3이 있으면 호출자 키 | 가장 높은 요청 빈도. 보호된 모든 요청 |
| `GET /login`, `POST /login/<p>`, `GET /callback/<p>`, `GET/POST /logout`, `GET /stepup*` | 포털 라우트를 통한 포털 리스너 | 인터넷 | 브라우저 입력만 |
| `GET /healthz` | 포털 리스너 | 게이트웨이를 통한 인터넷 | 비밀 정보 없음 |
| 관리 API와 콘솔(M4) | 관리 리스너 | 운영자 | CSRF, 출처 검사, 역할 |
| 아웃바운드: 제공자 디스커버리, JWKS, 토큰, 사용자 정보. SMTP. 웹훅 | Hopae → 인터넷 | — | SSRF와 응답 크기 제어 |
| 저장소 연결 | Hopae → SQLite 파일, PostgreSQL, Redis | — | 사설 네트워크. 원격 Redis/PostgreSQL에는 TLS |
| 설정 파일과 환경 | 프로세스 시작, 다시 로드(M6) | 운영자 | 검증됨. 비밀 정보는 참조로만 |
| 업데이트 매니페스트와 자산(M6) | Hopae → GitHub 릴리스 | — | 서명된 봉투 |

## 위협 목록

심각도는 프로세스의 척도를 따릅니다(S1 보안 경계 우회 … S4 외관상 문제).
"시나리오"는 해당 위협을 검증하는 시나리오를 가리킵니다.

| ID | 위협 | 흐름 | STRIDE | 의존하는 완화책 | 시나리오 |
| --- | --- | --- | --- | --- | --- |
| TM-01 | 돌아갈 URL을 통한 오픈 리디렉션: 공격자가 돌아갈 대상이 외부 사이트를 가리키는 로그인 링크를 만듦 | 1, 3, 4 | Tampering(변조), Spoofing(위장) | 포털은 클라이언트에서 돌아갈 URL을 절대 읽지 않습니다. 대상은 verify 호출에서 게이트웨이가 만든 `x-original-url`에서 가져와 트랜잭션에 저장하고, 검증(절대 URL, 허용된 스킴, 등록되었거나 기본 허용된 호스트, 2 KiB 이하, userinfo 없음, fragment 없음)한 뒤 그 호스트로 보내는 `Location`으로만 내보냅니다. 핸드오프 `302`는 게이트웨이가 보고한 URL에서 매개변수만 뺀 정확한 URL을 대상으로 합니다. | 005 |
| TM-02 | 쿠키 토싱: 형제 서브도메인이 설정한 쿠키를 애플리케이션 호스트가 자기 세션으로 제시함 | 4, 5 | Spoofing | `__Host-` 접두사: 브라우저는 `Domain` 속성이 있는 그런 쿠키를 거부하고, 형제의 호스트 전용 쿠키를 절대 보내지 않습니다. 알 수 없는 핸들은 채택하지 않으며, 핸들은 핸드오프 시 서버 측에서만 발급합니다. 접두사가 없는 개발 모드는 안전하지 않다고 문서화합니다. | 009 |
| TM-03 | 로그인과 로그아웃의 CSRF: 악성 페이지가 공격자 계정으로 로그인을 시작하거나(로그인 CSRF) 피해자를 로그아웃시킴 | 2, 3, 6 | Spoofing, Tampering | `POST /login/<p>`와 `POST /logout`은 `__Host-hopae_txn` 또는 `__Host-hopae` 쿠키에 바인딩된 CSRF 토큰과 포털 출처와 같은 `Origin`을 요구합니다. 콜백은 `state` ↔ 트랜잭션 쿠키 ↔ 제공자의 일치를 요구하므로 피해자가 공격자의 트랜잭션을 완료하게 만들 수 없습니다. `GET /logout`은 폼만 렌더링합니다. `SameSite=Lax` 쿠키. | 002, 006 |
| TM-04 | 세션 고정: 공격자가 로그인 전에 피해자의 브라우저에 알려진 핸들이나 트랜잭션을 고정함 | 2, 3, 4 | Spoofing | 핸들은 핸드오프 시 Hopae만 생성하고 다이제스트로 저장합니다. 클라이언트가 제시한 알 수 없는 핸들은 무시합니다. 트랜잭션 쿠키는 `/login`에서 교체되고 완료 시 지워집니다. 새 세션은 모든 호스트에서 새 핸들을 받고, 포털 핸들은 로그인 시 재발급됩니다. | 002, 003 |
| TM-05 | 핸드오프 코드의 재사용 또는 탈취(방문 기록, 로그, Referer, 어깨너머 엿보기) | 4 | Spoofing, Repudiation(부인) | 원자적 조건부 소비로 1회만 사용. 60초 수명. 대상 호스트, 경로, 로그인을 시작한 클라이언트 IP에 바인딩. 게이트웨이를 통해서만 소비(게이트웨이는 중계하는 `302`에 `referrer-policy: no-referrer`를 설정). 거부 시 `handoff.rejected`를 내보내고 IP별 제한(M2)에 집계. 코드는 업스트림에 절대 도달하지 않습니다. | 003 |
| TM-06 | 신원 헤더 위장: 클라이언트가 `x-forwarded-user`나 게이트웨이 맥락 헤더를 보냄 | 5 | Spoofing | 게이트웨이는 선언된 모든 신원 헤더 이름을 모든 수신 요청에서 제거하고 `x-forwarded-*`/`x-original-*`를 다시 생성합니다. Hopae의 게이트웨이 리스너는 클라이언트가 접근할 수 없고, 포털 리스너는 신뢰하지 않는 프록시의 `x-forwarded-*`를 무시합니다. 시나리오 007이 위장된 헤더가 업스트림에 절대 도달하지 않음을 증명합니다. | 007 |
| TM-07 | verify 엔드포인트의 서비스 거부: 무작위 핸들이나 긴 쿠키의 홍수. 느린 저장소 | 5 | Denial of service(서비스 거부) | verify는 제공자를 호출하지 않고 인덱스 조회 하나만 수행합니다. 쿠키 헤더는 8 KiB 이하이고 해시 전에 핸들 형식을 검사합니다. 알 수 없는 핸들에 대한 제한된 부정 캐시. 게이트웨이 리스너의 동시성 제한을 넘으면 `503`(거부 처리, 집계). 저장소 타임아웃. 게이트웨이의 `timeout_ms`가 클라이언트의 대기를 제한. 게이트웨이의 속도 제한과 실패 차단을 바깥 계층으로 사용. | 004 |
| TM-08 | 제공자 혼동: 제공자 A의 콜백이 제공자 B의 산출물로 완료되거나, 토큰 엔드포인트를 공격자 데이터에서 고름 | 3 | Spoofing, Elevation(권한 상승) | 각 트랜잭션은 선택한 제공자를 기록합니다. 콜백 경로는 제공자를 명시하고 일치해야 합니다. `state`는 (트랜잭션, 제공자)에 바인딩됩니다. 엔드포인트는 제공자 자체 설정 또는 설정된 발급자에서 가져온 디스커버리 문서에서만 옵니다. ID 토큰의 `iss`와 `aud`를 제공자 설정과 대조합니다. 제공자마다 별개의 `redirect_uri`. | 002, 012 |
| TM-09 | 이메일 충돌에 의한 계정 탈취: 제공자 B가 제공자 A로 만든 사용자의 이메일을 주장함 | 3 | Spoofing, Elevation | 연결 정책([ADR-0011](../adr/0011-account-linking-policy.md)): 주장하는 제공자가 이메일을 검증됨으로 보고하고 신뢰 목록에 있으며 기존 이메일도 검증된 경우에만 자동 연결합니다. Naver는 절대 자동 연결하지 않습니다(검증 플래그 없음). 그 외에는 별도 사용자를 만들거나 명시적 연결 흐름(M3)이 필요합니다. 제공자 측 이메일 변경은 신원을 다른 사용자로 옮기지 않습니다. | 002 (M1), 2xx (M3) |
| TM-10 | 웹훅 SSRF(M5): 대상이 내부 주소를 가리키거나 그곳으로 리디렉션함 | — | Information disclosure(정보 노출), Elevation | 대상은 `https`여야 합니다. 해석된 주소를 루프백, 사설, 링크 로컬, 멀티캐스트 범위와 대조하고 연결 동안 고정합니다(DNS 리바인딩 불가). 리디렉션을 따르지 않습니다. 본문 크기와 타임아웃 제한. HMAC 서명 페이로드. 대상 목록은 관리자만 관리. | 44x (M5) |
| TM-11 | Lua 샌드박스 탈출(M5) | — | Elevation | 스크립트는 게이트웨이의 모델을 따르는 별도 워커 프로세스에서 실행됩니다: `env_clear`, rlimit, seccomp 허용 목록, string/table/math 라이브러리만, 명령어와 메모리 예산, `SIGKILL`과 재시작을 수반하는 하드 타임아웃. 입력은 복사본이고 출력은 검증됩니다. 네트워크, 비밀 정보, 파일 시스템 없음. | 40x (M5) |

## 잔여 위험과 열린 질문

- 침해된 애플리케이션은 자기 사용자의 신원 헤더와 `x-hopae-session`을 읽을 수 있지만 세션을 만들 수는 없습니다. `x-hopae-session`을 애플리케이션별로 해시해야 하는지는 검토 과제로 남아 있습니다.
- strict IP 바인딩은 네트워크가 바뀐 모바일 사용자의 세션을 종료합니다. 기본값은 지시에 따라 strict이며, 운영자는 애플리케이션별로 완화할 수 있습니다. 위협 모델은 완화를 결함이 아니라 수용된 위험으로 다룹니다.
- 핸드오프 코드는 수명 동안 게이트웨이의 접근 로그에 나타납니다. 로그는 운영자의 자산이고 코드는 1회용입니다.
- HC-3이 출시되기 전까지 verify 호출자 인증은 순전히 네트워크 격리에 의존합니다.
