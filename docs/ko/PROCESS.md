# 개발 프로세스

<!-- translation-status: source=../PROCESS.md source-rev=1 status=current -->

[문서 목차](README.md) · [English](../PROCESS.md)

이 문서는 Hopae의 모든 변경을 설계하고, 검토하고, 테스트하고, 릴리스하고,
배포하는 방법을 정의합니다. 사람과 자동화된 에이전트 모두에게 구속력이 있습니다.
프로세스는 **책임과 증거**로 정의하며, 누가 또는 무엇이 그것을 만들어 냈는지로
정의하지 않습니다. 변경은 필요한 산출물이 존재하고 필요한 검사가 실행되었기
때문에 수락되는 것이지, 작성자의 역할 때문에 수락되는 것이 아닙니다.

최상위 규칙은 **게이트 ≠ 완료**입니다. 게이트 통과는 다음 단계로 가기 위한 필요
조건일 뿐, 변경이 끝났거나 올바르다는 증거가 아닙니다. "완료"는
[완료 정의](#완료-정의)에서 규정합니다.

## 역할

| 역할 | 책임 | 하지 않는 일 | 참여 시점 |
| --- | --- | --- | --- |
| 설계자 | 아키텍처와 설계 결정, 설계 문서와 [ADR](../adr/), 설계 검토 발견 사항에 대한 응답, 보안상 중요한 시나리오의 승인. | 일상적인 구현, 파일 단위 편집, 일반 버그의 분류. | 결정이 인터페이스, 신뢰 경계, 데이터 모델, 문서화된 보장을 바꿀 때, 또는 두 구현자의 의견이 갈릴 때. 기존 ADR이 이미 정한 작업에는 참여하지 않습니다. |
| 오케스트레이터 | 작업 분해, 파일 소유권을 명시한 작업 지시서, 통합, 게이트 검증, 검토 맥락 파일, 검토 발견 사항의 처리 결정, 커밋. | 조용한 범위 변경, 구현자의 보고를 증거 확인 없이 수락하는 일. | 모든 변경의 처음부터 끝까지. |
| 구현자 | 한 번에 하나의 작업 지시서, 그 지시서에 적힌 파일, 먼저 실패하는 테스트와 그다음 구현, 증거가 담긴 보고. | 지시서의 소유권 목록 밖 파일 편집(대신 오케스트레이터에게 요청), 테스트를 통과시키려고 테스트를 약화하거나 삭제하는 일, 아키텍처 결정. | 구현과 테스트 단계. 여러 구현자의 병렬 작업은 파일 소유권이 겹치지 않을 때만 가능합니다. |
| 적대적 검토자 | 제공된 맥락 파일을 바탕으로 설계, 분석, 코드를 독립적으로 반박. 심각도 순으로 정렬된 발견 사항과 각각의 구체적인 실패 시나리오, 참조 위치. | 코드 수정, 승인, 듣기 좋게 발견 사항을 완화하는 일. | 설계 검토(G2)와 코드 검토(G7), 그리고 다른 단계가 그 위에 쌓아 올릴 모든 분석. |
| 유지관리자(사람) | 범위, 릴리스, 배포에 대한 최종 권한, 비밀 정보와 릴리스 서명 시드의 보관. | 비밀 정보의 보관을 에이전트나 저장소 안의 파일에 위임하는 일. | 릴리스, 배포, 그리고 위 역할들이 상신하는 모든 결정. |

각 역할을 어떤 도구나 모델이 맡는지, 그리고 호출에 쓰는 정확한 명령은 공개하지
않는 `internal/PROCESS_ROLES.md`에 기록합니다. 공개 문서는 역할 이름만
적습니다. 책임은 안정적이지만 도구는 바뀌고, 도구의 세부 사항은 제품이 아니라
운영 환경에 속하기 때문입니다.

## 단계 게이트

모든 변경은 아래 게이트를 순서대로 통과합니다. 다음 게이트를 시작하기 전에 현재
게이트의 종료 체크리스트를 모두 충족해야 합니다. 게이트를 건너뛰려면 작업 기록에
서면 사유를 남기고 유지관리자의 동의를 받아야 하며, 보안 관련 변경은 G2, G7,
G8을 건너뛸 수 없습니다.

| 게이트 | 이름 | 주요 산출물 |
| --- | --- | --- |
| G1 | 설계 문서와 ADR | `docs/<TOPIC>.md` 초안과 `docs/adr/NNNN-*.md`(Proposed) |
| G2 | 적대적 설계 검토 | 검토 보고서(내부)와 ADR의 발견 사항 절 |
| G3 | 시나리오 명세 | `scenarios/NNN-*.md`(Approved) |
| G4 | 실패하는 테스트 | 시나리오 케이스 이름을 딴 테스트 함수, 기록된 실패 실행 |
| G5 | 구현 | 소유한 파일 안의 코드, 통과하는 테스트 |
| G6 | 자동 검사 | `make check`, `cargo test`, `cargo audit`, `make check-docs`, `make scenario-coverage` 모두 통과 |
| G7 | 적대적 코드 검토 | 검토 보고서(내부), 처리 결정 반영 |
| G8 | 실환경 종단 간 테스트 | 실행된 Hopae와 실제 게이트웨이, 가능하면 실제 제공자에 대해 시나리오 실행, `verified-live` 상태 |
| G9 | 배포 | 기준 배포 환경 갱신, 스모크 로그인 통과, 롤백 경로 확인 |

### G1 설계 문서와 ADR

진입: 동작을 바꾸는 로드맵 항목이나 결함.

종료 체크리스트:

- [ ] 설계 문서가 목표, 비목표, 인터페이스, 영향받는 데이터, 실패 동작, 운영자에게 보이는 효과를 명시한다.
- [ ] 인터페이스, 신뢰 경계, 데이터 모델, 보장을 바꾸는 모든 결정에 [템플릿](../adr/0000-template.md)을 사용한 `Proposed` 상태의 ADR이 있다.
- [ ] 보안 관련 변경이면 위협 모델(`docs/THREAT_MODEL.md`)에 변경분 초안이 있다: 새 자산, 진입점, 신뢰 경계, 의존하는 완화책.
- [ ] 미해결 질문을 명시적으로 나열했다. 본문 속에 숨긴 질문이 없다.

### G2 적대적 설계 검토

진입: G1 산출물이 존재한다.

종료 체크리스트:

- [ ] [검토 프로토콜](#적대적-검토-프로토콜)에 따라 검토 맥락 파일을 제공했다.
- [ ] 모든 S1, S2 발견 사항에 `FIX_FIRST` 처리를 적용했거나, 증거를 기록한 `REFUTED` 처리를 했다.
- [ ] ADR의 "Adversarial review" 절에 심각도별 발견 사항과 처리 결정을 적었다.
- [ ] 마지막 검토 패스에서 새로운 S1, S2 발견 사항이 없을 때만 ADR을 `Accepted`로 바꾼다.

### G3 시나리오 명세

진입: ADR 수락.

종료 체크리스트:

- [ ] 사용자나 보안 관점에서 보이는 모든 동작에 [템플릿](../../scenarios/000-template.md)을 사용한 시나리오가 `scenarios/`에 있다.
- [ ] 모든 시나리오에 정상 경로뿐 아니라 남용 케이스가 포함되어 있다.
- [ ] 모든 케이스에 계획된 테스트 이름과 종류(unit, integration, live)가 있다.
- [ ] 시나리오 상태가 `approved`이고, 보안상 중요한 시나리오는 설계자가 승인했다.

### G4 실패하는 테스트

진입: 승인된 시나리오.

종료 체크리스트:

- [ ] 각 시나리오 케이스에 [이름 규칙](#시나리오와-테스트의-대응)을 따르는 테스트가 있다.
- [ ] 각 테스트를 실행했고 **의도한 이유로 실패**했다(컴파일 오류나 픽스처 누락이 아니라 단언 실패). 실패 출력을 작업 기록에 첨부했다.
- [ ] 테스트가 실시간 대기(sleep), 루프백 밖의 네트워크 접근, 공유되는 가변 픽스처에 의존하지 않는다.

### G5 구현

진입: 실패하는 테스트가 기록되었다.

종료 체크리스트:

- [ ] 작업 지시서의 소유권 목록에 있는 파일만 바뀌었다. 예외는 오케스트레이터가 승인하고 기록했다.
- [ ] G4의 모든 테스트가 단언 수정 없이 통과한다. 테스트를 바꿀 때는 커밋 본문에 설명을 남긴다.
- [ ] 신뢰할 수 없는 입력 경로에 `unwrap()`/`expect()`가 없다. 오류는 타입이 있고 비밀 정보 없이 기록된다.
- [ ] 새 설정 키는 같은 변경에서 설정 참조 문서에 기록했다.

### G6 자동 검사

진입: 구현 완료.

종료 체크리스트(깨끗한 작업 트리에서 모두 실행하고 모두 통과해야 함):

- [ ] `make check` — `cargo fmt --all -- --check`와 `cargo clippy --all-targets --locked -- -D warnings`.
- [ ] `cargo test --locked --all-targets`.
- [ ] `cargo audit`에 처리되지 않은 권고가 없다. 수용한 권고는 `.cargo/audit.toml`에 사유와 만료일을 적어 둔다.
- [ ] `make check-docs` — 링크, 내비게이션, 제목 구조, 언어 배치, 번역 상태, 공개 정책.
- [ ] `make scenario-coverage` — 승인된 모든 시나리오 케이스가 존재하는 테스트에 대응하고, 시나리오 이름을 가진 모든 테스트가 시나리오에 대응한다.

### G7 적대적 코드 검토

진입: G6 통과.

종료 체크리스트:

- [ ] 주장, 참조 위치, 이전 보고서를 담은 검토 맥락 파일을 제공했다.
- [ ] 검토자의 기본 태도는 반박이었고, 발견 사항은 실패 시나리오와 함께 심각도 순으로 정렬되어 있다.
- [ ] S1/S2 발견 사항을 수정하고 재검증했다. S3는 수정하거나 시나리오로 추적한다. S4는 오케스트레이터 재량이다.
- [ ] 새로운 S1/S2 발견 사항이 없는 패스가 나올 때까지 반복했다. 각 패스에 이전 보고서 경로를 전달한다.

### G8 실환경 종단 간 테스트

진입: G7 완료.

종료 체크리스트:

- [ ] 시나리오의 주 흐름과 최소한 가장 심각도가 높은 남용 케이스를 모의 제공자만이 아니라 실행된 Hopae 바이너리 **와** 실제 게이트웨이 인스턴스에 대해 실행했다.
- [ ] 실제 제공자가 관련되고 테스트 테넌트가 있으면 주 흐름을 실제 제공자에 대해 실행했다. 그렇지 않으면 모의 실행을 증거의 상한으로 기록하고 시나리오는 `verified-live`가 아니라 `implemented`에 머문다.
- [ ] 실행 기록(날짜, 버전, 환경 라벨, 결과)을 시나리오의 실환경 검증 절에 첨부했다. 환경 라벨에는 내부 호스트 이름을 절대 쓰지 않는다.
- [ ] 모의 환경과 실환경의 동작 차이를 모의 제공자와 시나리오에 반영했다.

### G9 배포

진입: G8 완료, 릴리스 또는 사전 릴리스 태그 생성.

종료 체크리스트:

- [ ] 배포 환경의 실제 설정에 대해 설정 사전 점검을 통과했다(`hopae --check`).
- [ ] 변경 전에 상태를 백업했다. 이전 이미지나 바이너리를 롤백용으로 보관하고 있다.
- [ ] 배포를 교체했고, 게이트웨이를 통한 스모크 로그인과 로그아웃이 성공했다.
- [ ] 롤백을 마이너 버전마다 최소 한 번 리허설했다.
- [ ] 배포 영수증을 저장소가 아니라 내부 배포 기록에 적었다.

## 적대적 검토 프로토콜

검토자의 임무는 **반박**입니다. 기본 가정은 모든 주장이 틀렸다는 것, 모든 검사는
반대가 증명되기 전까지 눈속임이라는 것, 그리고 입력을 관측할 수 없는 게이트는
게이트가 없는 것보다 나쁘다는 것입니다. 이는 코드뿐 아니라 설계와 분석에도
적용됩니다. 기능 조사 결과, "이미 처리되어 있다"는 결론, 위협 모델 변경분도 그
위에 무언가를 쌓기 전에 같은 방식으로 검토합니다.

### 맥락 파일

오케스트레이터는 검토 패스마다 맥락 파일 하나를 작성합니다. 내용은 다음과 같습니다.

1. **범위** — 검토 대상과 명시적으로 제외하는 것.
2. **주장** — 변경이 의존하는, 번호가 붙은 반증 가능한 진술("C3: 재사용된 `state` 값은 토큰 교환 전에 거부된다").
3. **참조 위치** — 각 주장에 대한 파일 경로와 줄 범위, 시나리오 ID, ADR ID, 위협 모델 항목.
4. **이전 보고서** — 이 변경에 대한 이전 검토 보고서 경로와 각 발견 사항의 처리 결정.
5. **질문** — 오케스트레이터가 가장 확신하지 못하는 구체적인 지점.
6. **규칙** — 심각도 척도, 출력 형식, "수정하지 말고 반박만 할 것".

### 심각도 척도

| 심각도 | 의미 | 필수 처리 |
| --- | --- | --- |
| S1 | 보안 경계 우회, 데이터 손실, 또는 문서가 약속하지만 지켜지지 않는 보장 | 병합 전 `FIX_FIRST`, 또는 재현된 증거가 있는 `REFUTED` |
| S2 | 문서화된 흐름에서 사용자나 운영자가 도달할 수 있는 정확성 결함 | 병합 전 `FIX_FIRST` |
| S3 | 드문 설정에서만 도달하는 결함, 또는 빠진 남용 케이스 | 변경 안에서 `FIX`, 또는 시나리오와 로드맵 항목을 둔 `DEFERRED` |
| S4 | 스타일, 이름, 명료성 | 오케스트레이터 재량 |

### 출력과 처리 결정

각 발견 사항은 ID, 심각도, 반박하는 주장, 구체적인 실패 시나리오(입력, 순서,
관측값 대 기대값), 참조 위치, 제안하는 수정을 적습니다. 오케스트레이터는 발견
사항마다 처리 결정을 기록합니다: `FIX_FIRST`, `FIX`, `REFUTED`(증거로, 주장만으로는
안 됨), `DEFERRED`(추적 시나리오와 함께). 검토 보고서와 맥락 파일은
`internal/reviews/` 아래에 두고 공개하지 않습니다. 공개 기록은 ADR의 검토 절,
CHANGELOG의 `Security` 항목, 위협 모델입니다.

## 시나리오 기반 TDD

시나리오는 설계와 테스트 사이의 실행 가능한 계약입니다. 시나리오가 없는 동작은
명세되지 않은 것이고, 테스트가 없는 시나리오는 구현되지 않은 것입니다.

### 시나리오 파일

- 시나리오마다 파일 하나: `scenarios/NNN-kebab-name.md`, [템플릿](../../scenarios/000-template.md)에서 시작합니다.
- `NNN` 범위는 영역별로 할당합니다([`scenarios/README.md`](../../scenarios/README.md) 참고). 로드맵은 이 범위를 참조합니다.
- 각 시나리오에는 목표, 전제 조건, Given/When/Then 형식의 주 흐름, 대안 흐름, **필수 남용 케이스**, 관측 가능성 기대치, 테스트 대응 표, 실환경 검증 기록이 있습니다.
- 상태 수명 주기: `draft` → `approved` → `implemented` → `verified-live`. 상태는 오케스트레이터나 설계자만, 게이트 증거가 있을 때만 바꿉니다.
- 남용 케이스는 최소한 다음을 고려해야 합니다: 재사용(replay), 변조, 경쟁 조건/타이밍, 자원 고갈, 혼동된 대리인(confused deputy), 위조되거나 중복된 헤더, 프로토콜 다운그레이드, 열거(enumeration). 어떤 범주가 해당하지 않으면 사유와 함께 그렇게 적을 수 있습니다.

### 시나리오와 테스트의 대응

- 테스트 함수 이름은 소문자 시나리오 케이스 ID로 시작합니다: 시나리오 `012`, 케이스 `012-3` → `fn s012_3_<slug>()`; 남용 케이스 `012-A2` → `fn s012_a2_<slug>()`.
- 통합 테스트는 `tests/scenarios/`에 두며, 시나리오당 파일 하나(`s012_<slug>.rs`) 또는 시나리오가 작으면 영역당 파일 하나로 둡니다. 단위 테스트도 시나리오 이름을 가질 수 있지만, 시나리오가 사유와 함께 `unit-only`로 표시하지 않는 한 모든 시나리오 케이스에는 통합 수준 테스트가 최소 하나 필요합니다.
- 시나리오의 테스트 대응 표에 모든 테스트 이름과 파일을 적습니다. `make scenario-coverage`는 양방향을 검사합니다: 나열된 각 테스트가 존재하는지, 그리고 `sNNN_` 테스트 각각이 시나리오에 나열되어 있는지. 시나리오가 `approved`가 되면 대응되지 않은 항목은 빌드를 실패시킵니다.

### 테스트 하네스

| 계층 | 실행 대상 | 사용처 |
| --- | --- | --- |
| 단위 | 시계와 난수를 주입한 순수 함수와 상태 기계 | `unit`으로 표시한 케이스 |
| 통합 | 임시 상태 디렉터리를 가진 루프백의 Hopae 바이너리와 저장소 안의 모의 OAuth/OIDC 제공자 | 기본적으로 모든 시나리오 케이스 |
| 게이트웨이 | 통합 계층에 더해 `HOPAE_E2E_GATEWAY_BINARY`가 가리키는 실제 게이트웨이 바이너리. 게이트웨이는 실행된 Hopae로 인증을 전달하는 임시 라우트로 설정됨 | 포워드 인증, 헤더 주입, 경로 범위 케이스. 변수가 없으면 실패가 아니라 건너뜀 |
| 실제 제공자 | 게이트웨이 계층에 실제 제공자 테넌트를 더함. 자격 증명은 실행 시 개인 환경 파일에서 읽음 | G8 전용. `cargo test`에서는 절대 실행하지 않음 |

모의 제공자 요구 사항: PKCE와 nonce가 있는 authorization-code 흐름, 디스커버리
문서, 키 교체가 가능한 JWKS, 그리고 전환 가능한 오동작(잘못된 `state`, 잘못된
`nonce`, 만료된 토큰, 불일치하는 `aud`, 느린 응답, 잘못된 서명, 과대한 응답).
모의 제공자가 표현할 수 있는 모든 남용 케이스는 수동 테스트에 맡기지 않고
그곳에서 표현해야 합니다.

### 커버리지 추적

- `make scenario-coverage`는 표를 출력합니다: 시나리오, 상태, 케이스, 대응된 테스트, 빠진 테스트, 고아 테스트. `approved` 이상의 시나리오에서 빠진 항목이나 고아 항목이 있으면 CI가 실패합니다.
- `make coverage`는 단위와 통합 테스트에 대해 `cargo llvm-cov`를 실행합니다. 줄 커버리지는 진단 지표이지 게이트가 아닙니다. 게이트는 시나리오 커버리지입니다.
- 로드맵은 마일스톤별 시나리오 범위를 나열합니다. 마일스톤은 범위 안의 모든 시나리오가 `verified-live`이거나, 실환경 검증이 불가능한 사유와 함께 명시적으로 `implemented`로 표시되었을 때 완료됩니다.

## 브랜치, 커밋, 워크트리

- `main`은 항상 릴리스 가능해야 합니다. 작업은 `<type>/<slug>` 이름의 단명 브랜치에서 하며, 타입은 `feat`, `fix`, `sec`, `docs`, `test`, `refactor`, `chore`입니다.
- 병렬 작업은 현재 `main`에서 만든 별도 워크트리를 사용합니다. 워크트리마다 소유자 한 명과 작업 지시서 하나입니다.
- `main` 위로 리베이스하고 fast-forward로 통합합니다. `main`에 병합 커밋을 두지 않습니다.
- 커밋 제목은 명령형, 72자 이하이며, 운영자 관점에서 무엇이 바뀌었는지 말합니다. 본문은 이유, 무엇을 어떻게 검증했는지를 말합니다.
- 트레일러가 추적성을 담습니다. 해당하는 것을 사용합니다:

```text
Scenario: 012, 013
ADR: 0004
Threat-Model: updated
```

`Threat-Model:`은 모든 보안 관련 변경에 필수이며 `updated`, `reviewed`(변경 불필요,
검토함), `n/a` 중 하나를 씁니다. 지원 세션에서 만든 커밋에는 세션이 제공하는
귀속 트레일러도 마지막에 덧붙입니다.

- 커밋 하나에 논리적 변경 하나. 한 동작에 대한 두 언어의 문서, 시나리오, 테스트, 코드는 같은 커밋이나 같은 검토된 시리즈에 속합니다.
- 비밀 정보, 생성된 산출물, 로컬 설정, 내부 문서, 내부 인프라 이름이 들어간 파일은 절대 커밋하지 않습니다. 사전 커밋 훅과 `make check-docs`가 이를 거부하지만, 훅은 안전망이지 규칙 자체가 아닙니다.

## 변경 이력과 버전

- `CHANGELOG.md`는 [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/)을 따릅니다: `Unreleased` 절과 버전별 절, 그리고 `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` 하위 절.
- 사용자에게 보이는 모든 변경은 같은 커밋에서 항목을 추가합니다. 보안 수정은 버그 수정이기도 하더라도 항상 `Security` 아래에 둡니다.
- 버전은 [Semantic Versioning 2.0.0](https://semver.org/)을 따릅니다. 1.0.0 이전에는 마이너 버전이 설정이나 게이트웨이 계약의 호환성 깨는 변경을 포함할 수 있으며, 각각을 `Changed` 아래에 마이그레이션 메모와 함께 나열합니다. 패치 버전은 설정을 절대 깨지 않습니다.
- 설정 스키마와 포워드 인증 응답 계약은 버전 관리 관점에서 공개 API의 일부입니다.

## 릴리스와 서명

자가 업데이트는 Hangang의 서명된 업데이트와 Sugyeol의 GitHub 릴리스 탐색과 같은
방식으로, 정확한 릴리스 산출물에 대한 Ed25519 서명 매니페스트를 검증합니다. 검증
키는 `release-public-key.txt`에 공개합니다. 서명 시드는 유지관리자가 오프라인으로
보관하며 저장소, 공개 바이너리의 빌드 환경, 어떤 에이전트의 맥락에도 절대 들어가지
않습니다. 봉투 형식, 탐색, 다운그레이드 방지, 롤백의 세부 사항은 마일스톤 M6
전에 전용 ADR에서 결정하며, 이 체크리스트를 다듬을 수 있습니다.

릴리스 체크리스트:

- [ ] `main`이 G6에서 통과했고 마일스톤의 시나리오가 `verified-live`다.
- [ ] `Cargo.toml`의 버전을 올렸다. `CHANGELOG.md`의 `Unreleased`를 날짜와 함께 새 버전으로 옮겼다.
- [ ] 위협 모델과 설정 참조 문서가 릴리스를 반영한다.
- [ ] 릴리스 커밋에 주석 태그 `vMAJOR.MINOR.PATCH`를 만들었다.
- [ ] 태그된 커밋에서 지원 대상별로 `--locked`로 정적 바이너리를 빌드했다.
- [ ] 릴리스 자산을 준비했다: 대상별 원시 실행 파일, `<binary>-<target>.manifest.json`(서명된 봉투: 버전, 대상, 산출물 URL, SHA-256, 크기), `SHA256SUMS`.
- [ ] `release-public-key.txt`와 짝이 되는 시드로 매니페스트를 오프라인에서 서명했다. 업로드 전에 공개 키로 서명을 검증했다.
- [ ] 실행 파일을 먼저, 매니페스트를 마지막에 업로드했다. 릴리스를 정식(stable)으로 표시했다(업데이트 대상 릴리스는 절대 초안이나 사전 릴리스가 아니어야 함).
- [ ] 이전 버전에서 `hopae --check-update`를 실행하면 서명된 자산이 있는 새 버전이 보고된다.
- [ ] 배포는 G9를 따른다.

## 보안 규칙

이 규칙은 코드, 테스트, 문서, 커밋 메시지, 검토 맥락 파일, 작업 지시서에 모두
적용됩니다.

- [ ] **저장소에 비밀 정보를 절대 넣지 않는다.** 토큰, 클라이언트 비밀, 서명 시드, 쿠키, 세션 키는 저장소 밖의 개인 환경 파일(관례적으로 `~/env`)이나 배포 환경의 비밀 저장소에서 실행 시에 읽는다. 그 값은 소스, 픽스처, 문서, 로그, 테스트 출력, 커밋 메시지에 절대 쓰지 않는다. 자격 증명이 필요한 테스트는 환경에서 읽고, 없으면 건너뛴다.
- [ ] **공개 산출물에 내부 인프라를 넣지 않는다.** 운영자 환경의 호스트 이름, 내부 도메인, IP 주소, 장비 라벨, 배포 경로, 계정 이름은 `internal/` 아래에만 둔다. 공개 예제는 루프백 주소와 `*.example.test` 이름을 쓴다. 공개 검사기는 거부 목록을 저장소 밖 파일에서 읽으므로 거부 목록 자체가 공개되지 않는다.
- [ ] **모든 보안 관련 변경은 위협 모델을 따른다.** 인증, 세션 처리, 쿠키, 게이트웨이에서 받거나 게이트웨이로 내보내는 헤더, 암호, 속도 제한, 블랙리스트, 관리자 접근, 웹훅, Lua 훅, 업데이트 검증, 개인 정보 저장을 바꾸는 변경은 같은 변경에서 `docs/THREAT_MODEL.md`를 갱신하고 `Threat-Model: updated`를 단다.
- [ ] **거부 처리(fail closed)한다.** 필수 검사를 실행할 수 없을 때(저장소 사용 불가, 허용 범위를 넘는 시계 차이, 제공자 연결 불가) 요청을 거부하고 기록하고 집계한다. 의존성 부재가 "허용"으로 완화되는 일은 없다.
- [ ] **직접 만든 암호를 쓰지 않는다.** 감사된 크레이트를 쓰고, 비밀 비교는 상수 시간으로, 난수는 운영체제 CSPRNG에서 얻으며, 키 교체는 설정으로만 하고 검증 대상이 보낸 메시지로는 절대 하지 않는다.
- [ ] **신원 헤더는 게이트웨이 계약이 소유한다.** Hopae는 게이트웨이의 인증 확인에만 신원을 내보낸다. 클라이언트가 보낸 해당 헤더의 복사본은 절대 신뢰하지 않으며, 계약 문서는 게이트웨이가 그것을 어떻게 제거하는지 기술한다.
- [ ] **로그와 감사 기록에는 식별자만 담고 자격 증명은 담지 않는다.** 주체 ID, 세션 ID(bearer 토큰인 경우 해시), 제공자 이름, 결정과 사유 코드만 담고, 토큰, 비밀번호, 코드, 전체 쿠키는 절대 담지 않는다.
- [ ] **의존성을 감사한다.** G6에서 `cargo audit`을 실행한다. 새 의존성은 커밋 본문에서 정당화한다. 빌드는 `--locked`로만 한다.
- [ ] **에이전트는 자격 증명 저장소를 절대 스캔하지 않는다.** 자동화된 역할은 작업 지시서에 적힌 파일만 읽는다. 값을 "찾아내기" 위해 프로세스 환경, 토큰 파일, 개인 디렉터리를 뒤지지 않는다.

## Make 대상

`Makefile`은 다음 대상을 제공하며, 게이트는 이 이름으로 참조합니다. 대상은
마일스톤 M0에서 만들고 이 이름을 유지해야 합니다.

| 대상 | 실행 내용 |
| --- | --- |
| `make check` | `cargo fmt --all -- --check`; `cargo clippy --all-targets --locked -- -D warnings` |
| `make test` | `cargo test --locked --all-targets`(모의 제공자를 사용하는 단위와 통합 테스트) |
| `make audit` | `cargo audit` |
| `make check-docs` | Git 인덱스에 대한 링크, 내비게이션, 제목, 언어 배치, 번역 상태, 공개 정책 검사 |
| `make scenario-coverage` | 시나리오와 테스트의 교차 검사 |
| `make gates` | `check`, `test`, `audit`, `check-docs`, `scenario-coverage`를 순서대로 실행 |
| `make e2e` | 게이트웨이 계층 시나리오. `HOPAE_E2E_GATEWAY_BINARY` 필요 |
| `make coverage` | `cargo llvm-cov` 보고서 |
| `make static` | 정적 Linux 릴리스 빌드 |
| `make release-assets` | 서명을 위한 바이너리, 매니페스트, `SHA256SUMS` 패키징 |

## 완료 정의

변경은 모든 게이트를 통과한 것에 더해 다음이 모두 성립할 때 완료입니다.

- [ ] 동작이 시나리오에 존재하고, 시나리오가 `verified-live`이거나 실환경 검증이 불가능한 사유가 기록되어 있다.
- [ ] 오케스트레이터가 구현자의 보고에 의존하지 않고 시나리오 케이스 하나와 남용 케이스 하나를 직접 다시 실행했다.
- [ ] 영문 문서와 한국어 번역을 같은 변경에서 갱신했고 `make check-docs`가 통과한다.
- [ ] 위협 모델, 설정 참조 문서, CHANGELOG를 갱신했다.
- [ ] 열린 S1, S2 검토 발견 사항이 없다. 유예한 S3 발견 사항에는 시나리오가 있다.
- [ ] 운영자가 문서화된 절차로 변경을 롤백할 수 있다.
- [ ] diff에 내부 이름, 비밀 정보, 생성된 산출물이 없다.

위 항목 없이 `make gates`만 통과한 것은 완료가 아니라 검토 준비 상태입니다.

호패 artifact는 `tools/prepare_release.py --target TARGET --output OUTPUT --signer
OFFLINE_SIGNER --seed PRIVATE_SEED_FILE`로 서명 준비합니다. 비공개 시드는 저장소 공개
키와 일치해야 하고 서버·저장소에 넣지 않습니다. 수문장의 정확한 payload bytes·base64
서명 envelope와 같은 방식을 쓰며 별도로 서명·payload·artifact 해시를 검증합니다.
호패 자동 self-update는 아직 미구현이므로 이번 서명 artifact로 지원을 주장하지 않습니다.

## 네이티브 macOS 검증 사전 조건

대상 OS에서 단위·통합·시나리오 테스트를 직렬 실행합니다. 크로스 빌드나 `--version`
확인만으로 런타임 검증을 완료할 수 없습니다. peer 격리 시나리오는 `127.0.0.2`에
바인딩합니다. macOS에서는 실행 전에 해당 loopback alias를 준비하고 기존 alias는
유지하며 검증을 위해 새로 만든 alias만 실행 후 제거합니다. Linux는 loopback subnet을
기본 제공하고 RSS는 실제 자식 프로세스의 Linux `/proc`·macOS `/bin/ps`로 검사합니다.
감사 출력 실패는 Linux 전용 `/dev/full` 대신 상대가 닫힌 Unix socket으로 재현하며
grant·필수 감사 기록의 검증은 유지합니다.

raw 테스트 client는 명시적인 HTTP framing으로 응답 전체를 받은 경우에만 연결
초기화를 허용합니다. framing이 없거나 잘렸거나 모호하면 계속 실패합니다. loopback
HTTPS verifier fixture는 시작 시 hostname을 조회하지 않아 준비가 외부 DNS에 의존하지
않습니다. 이 harness 수정은 릴리스 실행 파일에 test hook을 켜거나 인증 동작을
바꾸지 않습니다.
