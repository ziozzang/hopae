# 로드맵

<!-- translation-status: source=../ROADMAP.md source-rev=7 status=current -->

[문서 목차](README.md) · [English](../ROADMAP.md)

이 페이지는 작업의 순서를 정합니다. 프로젝트 브리프와 게이트웨이의 기존 기능
조사에서 도출했으며, 마일스톤의 범위나 순서가 바뀔 때마다 갱신합니다. 완료된
항목은 [CHANGELOG](../../CHANGELOG.md)로 옮깁니다. 시나리오 번호 범위는
[`scenarios/README.md`](../../scenarios/README.md)에 정의되어 있습니다.
마일스톤이 구현하는 설계는 [아키텍처](ARCHITECTURE.md),
[게이트웨이 계약](GATEWAY_CONTRACT.md), [위협 모델](THREAT_MODEL.md),
그리고 ADR-0002부터 ADR-0016까지에 있습니다.

## 제품의 형태

Hopae는 Hangang 게이트웨이 앞에 서는 것이 아니라 게이트웨이를 **중심으로**
패키징됩니다. 게이트웨이는 이미 외부 인증 확인을 수행하고, 검증된 신원 헤더를
업스트림 요청에 주입하며, 클라이언트가 보낸 복사본을 제거합니다. Hopae는
게이트웨이에 없는 것, 즉 로그인 포털, 제공자, 세션, 정책을 제공합니다.

```text
 브라우저               Hangang(게이트웨이)                    Hopae                      제공자
   │  GET app.example.test/admin  │                              │                          │
   ├─────────────────────────────▶│  포워드 인증 GET /_hopae/verify                          │
   │                              ├─────────────────────────────▶│ 세션 없음                 │
   │  302 auth.example.test/login │◀─────────────────────────────┤ 302 + 트랜잭션            │
   │◀─────────────────────────────┤                              │                          │
   │  GET auth.example.test/login (같은 게이트웨이의 라우트)        │                          │
   ├─────────────────────────────▶├─────────────────────────────▶│ 제공자로 302              │
   │◀─────────────────────────────┴──────────────────────────────┤                          │
   ├──────────────────────────────── 인가, 동의 ────────────────────────────────────────────▶│
   │◀─────────────────────────────── 302 /callback?code ────────────────────────────────────┤
   ├─────────────────────────────▶├─────────────────────────────▶│ code → 토큰, 세션 생성     │
   │  302 app.example.test/admin?_hopae_handoff=K                │ Set-Cookie(포털 호스트)    │
   │◀─────────────────────────────┴──────────────────────────────┤                          │
   ├─────────────────────────────▶│  포워드 인증 GET /_hopae/verify(핸드오프)                 │
   │  302 app.example.test/admin + Set-Cookie(앱 호스트)          │ 코드 소비, 핸들 발급       │
   │◀─────────────────────────────┤◀─────────────────────────────┤                          │
   ├─────────────────────────────▶│  포워드 인증 GET /_hopae/verify                          │
   │                              ├─────────────────────────────▶│ 세션 유효                 │
   │                              │  200 + 신원 헤더              │                          │
   │                              │◀─────────────────────────────┤                          │
   │                              ├── x-forwarded-user 등을 담은 업스트림 요청 ──▶ 앱        │
   │                              │   (클라이언트가 보낸 해당 헤더 복사본은 제거됨)             │
```

로드맵이 의존하는 사실들입니다. 2026-10-09에 게이트웨이에서 관찰했으며, 같은
날 M0/M1 설계 게이트에서 게이트웨이 소스(`src/proxy.rs`, `src/config.rs`)에
대해 다시 확인했습니다.

- 게이트웨이의 외부 확인은 본문 없는 고정 URL `GET`입니다. 나열된 클라이언트 헤더(세션 쿠키 포함)만 전달되고, 원래 URL, 메서드, 클라이언트 IP 같은 게이트웨이 생성 맥락 헤더가 더해집니다. HTTP/2에서 분할된 `cookie` 필드는 먼저 합쳐집니다.
- `2xx` 응답은 요청을 허용하고 나열된 응답 헤더를 업스트림에 주입합니다. `302`/`401`/`403` 응답은 `forward_response`가 켜져 있을 때 `Location`과 `Set-Cookie`와 함께 브라우저로 중계될 수 있습니다. 타임아웃을 포함한 그 밖의 모든 경우는 거부 처리됩니다.
- 어떤 라우트의 응답 목록에든 선언된 신원 헤더 이름은 게이트웨이 전체에서 모든 수신 요청으로부터 제거됩니다.
- 게이트웨이는 인증 결정을 캐시하지 않습니다. verify 엔드포인트는 모든 요청마다 호출되므로 빨라야 하며, 취소(revocation)가 동작하는 이유도 이것입니다. 마이크로 캐시는 제안된 게이트웨이 변경(HC-1)이며 기본적으로 꺼져 있습니다.
- 경로 범위 지정은 라우트 단위입니다(`path_prefix`, 매칭 모드, 우선순위). 더 세밀한 규칙은 원래 URL 헤더를 사용해 Hopae 안에 둡니다.
- 로그인 제한, 블랙리스트, 로그인 기록은 게이트웨이 기능이 아닙니다. 게이트웨이의 URL별 실패 차단은 바깥 계층이 될 수 있습니다.
- 게이트웨이의 Lua 정책 API는 응답 헤더, 쿠키, 리디렉션을 설정할 수 없습니다. 따라서 애플리케이션 호스트의 로그인·로그아웃 진입점은 Hopae에(또는 네이티브 게이트웨이 변경 HC-5에) 둡니다.
- 게이트웨이는 외부 확인 호출에 정적 헤더를 더할 수 없으므로, verify 엔드포인트에는 네트워크 도달 범위 외의 호출자 인증이 없습니다. 호스트 네트워크로 동작하는 게이트웨이에서는 루프백이 어떤 로컬 프로세스든 받아들입니다. 따라서 게이트웨이 변경 HC-3은 M1과 함께 구현합니다.
- 라우트는 정규화된(디코딩·정규화된) 경로로 선택되지만 외부 확인은 원래 경로를 그대로 받습니다. 외부 확인의 `429`는 `503`이 됩니다. `x-original-*` 헤더는 외부 확인이 없는 라우트에서 변경 없이 그대로 통과합니다.

## 마일스톤

각 마일스톤은 범위 안의 모든 시나리오가 `verified-live`(또는 사유를 기록한
`implemented`)이고, 두 언어의 문서, 위협 모델 갱신, CHANGELOG 절, G9에 따른
배포가 있을 때 끝납니다. 버전은 참고용입니다.

### M0 — 기반(0.0.x)

목표: 빈 크레이트 위에서 프로세스가 끝까지 돌아간다.

- [ ] Cargo 워크스페이스, [이름이 정해진 대상](PROCESS.md#make-대상)을 가진 `Makefile`, 사전 커밋 훅(비밀 정보 스캔, 공개 검사), `make gates`를 실행하는 CI.
- [ ] [문서 체계](DOCUMENTATION.md#검증)에 명시한 `tools/check_docs.py`와 `tools/scenario_coverage.py`. ADR-0013의 `make check-boundary` 린트.
- [ ] 프로세스와 시나리오 002, 012에 나열한 오동작 프로필을 갖춘 `tests/support/mock_idp`의 모의 OAuth/OIDC 제공자(`oidc`와 `oauth2` 종류).
- [ ] Hopae 바이너리를 실행하고 탐침하는 통합 하네스. `HOPAE_E2E_GATEWAY_BINARY` 뒤의 게이트웨이 계층. 에코 업스트림. `__Host-`와 `SameSite` 규칙을 구현한 쿠키 저장소 클라이언트.
- [x] `docs/ARCHITECTURE.md`, `docs/GATEWAY_CONTRACT.md`, `docs/THREAT_MODEL.md` v0 초안 작성(G1).
- [ ] 적대적 설계 검토(G2) 후 수락된 ADR-0002부터 ADR-0013: 저장소, HTTP 스택, 세션 모델과 도메인 간 핸드오프, 게이트웨이 계약과 버전 관리, verify 캐싱과 무효화, 맥락 바인딩, 2차 인증 확장 지점, 이벤트 모델, 제공자 추상화, 계정 연결, 서비스 등록과 게이트웨이 설정 소유권, 어댑터 경계.
- [x] M0 키와 ADR이 예정한 모든 키를 나열한 `docs/CONFIG.md`.

종료: 빈 크레이트에서 `make gates` 통과. 템플릿 시나리오 하나가 하네스 위에서 실행된다. ADR이 수락된다.

### M1 — 수직 슬라이스(0.1.0)

목표: 실제 사용자 한 명이 실제 게이트웨이를 거쳐 실제 제공자 하나로 로그인하고,
업스트림 애플리케이션이 검증된 신원 헤더를 받는다. 이 마일스톤은 의도적으로
좁으며, 어떤 폭 확장보다 먼저 완료합니다.

범위(시나리오 001–099):

- [ ] PKCE와 nonce, 그리고 사용자 정보 subject 일관성 검사를 갖춘 범용 OIDC authorization-code 클라이언트. 첫 설정 제공자는 Google(ADR-0010).
- [ ] SQLite 저장소의 서버 측 세션. 핸들별 타이머와 발급 수준을 가진 `__Host-hopae`의 호스트별 불투명 핸들. `state`로 찾는 로그인 트랜잭션. 애플리케이션 호스트(`__Host-hopae_bind`)와 포털(`__Host-hopae_portal`)의 브라우저별 안정적인 바인딩 쿠키와 첫 사용 경쟁에서의 깊이 제한 복구. 발급 시점의 인증 수준과 세션의 자격 증명 세대를 담은 일회용 도메인 간 핸드오프 코드. 이미 소비된 코드의 멱등 처리와, 매개변수를 실은 비문서 요청에 대한 중계된 `403`을 포함한 문서 탐색 전용 소비. `/switch` 계정 전환 확인. 수명 상태 기계(ADR-0002, ADR-0004, ADR-0007).
- [ ] 리스너 두 개: 게이트웨이(`/_hopae/verify`, 호출자 키 필수, 현재 키와 다음 키를 함께 받는 키 교체)와 포털(로그인, 제공자 콜백, 전환, 로그아웃, 상태 확인)(ADR-0005).
- [ ] 게이트웨이 변경 HC-3(호출자 키를 담은 정적 요청 헤더)을 게이트웨이 저장소에 구현하고, 빌드된 게이트웨이에 대해 시나리오 004-A8과 013-A1로 검증.
- [ ] 계약에 따른 `GET /_hopae/verify`: 신원 헤더 집합과 `x-hopae-fresh-until`, `x-hopae-gen`을 함께 담은 `200`. 정확히 등록된 출처인 돌아갈 대상과 함께 `302`. 문서 부트스트랩으로서 애플리케이션 URL을 알려 주고 아무것도 만들지 않는 `401`. 거부와 속도 제한에는 `403`. `400`/`503`은 거부 처리. 모든 응답에 `cache-control: no-store`(ADR-0006 기본값). 400 ms verify 예산.
- [ ] 정확한 호스트 이름, 포트, 수명, 바인딩 정책을 가진 애플리케이션 레지스트리(`apps[]`). 불일치 시 세션을 종료하는 클라이언트 IP 바인딩, 애플리케이션별 설정 가능(ADR-0007). 결정 입력의 정규화된 경로와 예약 매개변수 인식 규칙(ADR-0013).
- [ ] 기본적으로 명시적 연결을 요구하는 계정 생성 규칙: 이메일 충돌은 안내와 함께 거부(ADR-0011). 완료 흐름은 M3.
- [ ] 세션 스키마가 인증 요소와 `aal`을 기록. 핸들이 `issued_aal`을 기록. verify가 `x-hopae-aal`과 `x-hopae-factors`를 내보냄. 사용자가 매 verify마다 읽는 `authz_version`을 가짐(ADR-0008 스키마만).
- [ ] 트랜잭션 아웃박스로서의 이벤트 모델: 필수 이벤트와 싱크별 전달 행을 상태 변경과 함께 커밋, `event_id`로 중복을 제거하는 최소 1회 전달, 데드레터가 있는 싱크별 적체 상한, 이벤트와 함께 삭제되는 전달 행, 수치로 정한 정리 주기, 구조화 로그 싱크(ADR-0009).
- [ ] 헤더 주입 계약: 신원 헤더 집합, 클라이언트 복사본이 게이트웨이 전체에서 제거되도록 하는 게이트웨이 라우트 선언, 위조된 헤더가 업스트림에 절대 도달하지 않음을 증명하는 게이트웨이 계층 테스트.
- [ ] 게이트웨이 라우트를 통한 경로 범위 보호(공개 접두사, 보호 접두사, 더 높은 우선순위의 `/admin`)를 동작하는 라우트 예제와 함께 문서화. 0단계 수동 등록(ADR-0012). Hopae 측 경로별 규칙은 M2로 유예.
- [ ] `docs/CONFIG.md`에 문서화한 JSON 설정 파일, `hopae --check` 사전 점검, 사유 코드가 있는 구조화된 로그.
- [ ] Hopae를 게이트웨이 뒤에 두는 `deploy/` Compose 템플릿. 기준 환경에 배포.
- [ ] 첫 실제 배포 이후(ADR-0015, 제안됨): verify 호출 안에서 Hopae가 답하는 애플리케이션 호스트 진입점 `/_hopae/login`과 `/_hopae/logout`, 예약된 `/_hopae/` 이름 공간, 로그아웃 티켓, `apps[].logout_confirm`. 세션 핸들이 더 이상 업스트림에 도달하지 않도록 하는 게이트웨이 변경 HC-12(`auth.strip_request_cookies`). 계약 v1.1.

시나리오(G1에서 초안, G3에서 승인):

| ID | 제목 |
| --- | --- |

| 008 | 게이트웨이 라우트를 통한 경로 범위 보호 |

종료: 실제 게이트웨이의 보호된 라우트에서 브라우저가 실제 제공자로 로그인을
완료하고, 업스트림이 신원 헤더를 보며, 클라이언트가 보낸 신원 헤더는 제거되고,
호출자 키가 없는 verify 호출은 거부되며, 다른 등록 도메인의 두 번째
애플리케이션에 제공자 재로그인 없이 도달하고, 같은 IP 뒤의 두 번째 브라우저는
첫 브라우저의 핸드오프를 소비할 수 없으며, 로그아웃하면 다음 요청부터 접근이
끝난다.

### M4-min — 관리 콘솔 최소(0.2.0)

첫 실환경 배포 뒤 유지관리자의 요청으로 M2보다 앞당겼습니다. 폭을 넓히기 전에
관리 페이지가 필요합니다. [ADR-0016](../adr/0016-management-console-minimum.md)(Proposed)에서
설계하고 [관리 페이지](ADMIN.md)에서 명세하며, M4의 나머지는 아래 제자리에
남습니다. 이후 버전은 그에 따라 마이너 하나씩 밀립니다.

범위(300–399 범위 중 시나리오 300–305):

- [ ] 콘솔 호스트를 제공하는 세 번째 리스너 `listen.admin`. 콘솔 호스트는 `admin.public_url`로 등록되는 암묵적 애플리케이션 `admin`이며 게이트웨이의 보호 라우트(표준 `auth` 블록, `strip_request_cookies` 없음) 뒤에 있음. 모든 요청을 Hopae가 verify 엔진을 통해 `__Host-hopae` 핸들로 인증. 주입된 신원 헤더는 절대 읽지 않음.
- [ ] 부여된 사용자로서의 관리자: 마이그레이션 `0003`의 `admin_grants` 테이블(역할 `admin`, `viewer`). 부트스트랩과 복구를 위한 `hopae admin grant|revoke|list`. 요청마다 부여를 읽음. `admin.max_auth_age`와 `admin.require_aal`.
- [ ] 사용자: 목록과 검색, 신원·세션·최근 이벤트가 있는 상세. 비활성화(상태, `authz_version`, 살아 있는 모든 세션 종료)와 활성화.
- [ ] 세션: 사용자, 호스트, 생성, 마지막 활동, 클라이언트 주소, user-agent 접두사(`sessions.bound_ua_prefix`), 수준이 있는 살아 있는 세션. 하나 종료. 사용자의 모든 세션 종료.
- [ ] 로그인 기록과 감사: 필터(종류, 결과, 사용자, 세션, 클라이언트 주소, 시간 범위)와 키셋 페이지 나누기가 있는 `events` 조회. 인덱스 `events(kind, at)`, `sessions(terminated_at, last_seen_at)`, `users(created_at)`.
- [ ] 읽기 전용 상태: 애플리케이션, 제공자(활성 여부, `managed_by`, 상태, 비밀 변수 이름과 존재 여부), 저장소, 빌드, 설정 세대.
- [ ] 모든 변경을 같은 트랜잭션의 `admin.*` 이벤트로 감사하고 쓰기 안에서 행위자를 다시 검사. 모든 거부에 `admin.denied`.
- [ ] 스크립트 없는 영어/한국어 서버 렌더링 페이지, 포털의 CSP와 보안 헤더, 핸들에 바인딩된 CSRF 토큰과 `Origin`. 사용자 정의 헤더와 content-type 규칙을 가진 JSON `/v1` API.
- [ ] `hopae --check`가 콘솔 라우트 조각을 출력. 배포 템플릿에 리스너와 라우트 예시 추가.

| ID | 제목 |
| --- | --- |
| 300 | 콘솔에 대한 관리자 접근: 핸들 인증, 부여, 역할, 신선도, CSRF, 직접 연결 |
| 301 | 콘솔 사용자: 목록, 검색, 상세, 비활성화와 활성화 |
| 302 | 콘솔 세션: 살아 있는 세션 목록, 하나 종료, 사용자의 전체 종료 |
| 303 | 콘솔 로그인 기록과 감사 조회 |
| 304 | 콘솔 상태는 읽기 전용이며 비밀을 보여 주지 않음 |
| 305 | 명령줄의 관리자 부여: 부트스트랩, 취소, 목록, 복구 |

종료: 실환경 게이트웨이를 통해 부여된 사용자가 자체 호스트의 콘솔을 열고, 부여
없는 사용자는 거부되고, 비활성화된 사용자의 세션은 모든 호스트의 다음 요청에서
거부되고, 종료된 세션은 거부되고, 모든 작업에 `admin.*` 기록이 있고, 위조된
신원 헤더로 게이트웨이를 우회한 요청은 거부된다.

### M2 — 세션, 남용 제어, 공유 상태(0.3.0)

범위(시나리오 100–199):

- [ ] `events` 테이블 위의 로그인 기록 API: 사용자, IP, 제공자, 결과, 시간으로 필터. 보존 기간 제한. 콘솔 화면, `/v1/events` 조회, 정확한 주소와 시간 필터는 M4-min에서 제공하며 M2는 제공자와 CIDR 필터, 보존 제어를 더합니다.
- [ ] 블랙리스트: 주체, 이메일, 이메일 도메인, 클라이언트 IP(CIDR). 로그인과 verify에서 검사. 관리자가 관리.
- [ ] 계정별, 클라이언트 IP별 로그인 시도 제한과 잠금. 동기적이고 원자적인 카운터와 일정한 작업량의 응답. 게이트웨이의 실패 차단과의 상호작용 문서화.
- [ ] 인스턴스 두 개가 하나의 디렉터리를 공유하도록 하는 기본 저장소의 PostgreSQL 백엔드(ADR-0002).
- [ ] 세대 번호가 붙은 무효화 채널과 시도 횟수 카운터로만 쓰는 Redis/Valkey(50 ms 작업, 차단기, 카운터는 거부 처리). Redis에는 세션이나 결정 상태를 두지 않음. 세대 출처를 담은, 옵트인 방식의 제한된 Hopae 로컬 캐시(권위 있는 읽기의 캐시)(ADR-0006). 애플리케이션별 `verify_cache_seconds`, `x-hopae-fresh-until`, `x-hopae-gen`. 그룹, 상태, 취소, 단계 상승 변경 시 `authz_version`과 `cred_gen` 무효화. 더 낮은 세대로 복원해도 모든 캐시가 복구되도록 하는 데이터베이스 에포크와 `hopae store mark-restored`(ADR-0006 결정 8).
- [ ] 사용자를 위한 모든 기기에서 로그아웃(`scope=all`). 관리자 취소와 주체별 세션 목록은 M4-min에서 제공합니다.
- [ ] 원래 URL로 평가하는 Hopae 측 경로와 호스트 정책 규칙(허용, 로그인 필요, 그룹 필요). 이런 규칙이 있으면 해당 애플리케이션의 결정은 `no-store`로 표시.
- [ ] 게이트웨이 설정 소유권 1단계(ADR-0012): `hopae gateway render`와 읽기 전용 불일치 보고.

종료: 게이트웨이 뒤의 PostgreSQL 기반 Hopae 인스턴스 두 개가 세션을 공유하고
서로의 캐시를 무효화한다. 잠금, 블랙리스트, 취소를 실환경에서 검증한다.

### M3 — 제공자(0.3.0)

범위(시나리오 200–299):

- [ ] ADR-0010에 따른 카카오(사용자 정보 검증 특이 사항이 있는 OIDC 프리셋)와 네이버(프로필 매핑이 있고 검증 플래그가 없는 `oauth2` 프리셋). 공식 문서는 G1에서 다시 확인.

- [ ] 실행 중 제공자 활성화/비활성화와 순서 지정. 제공자별 허용 이메일 도메인.
- [ ] ADR-0011에 따른 명시적 계정 연결 흐름과 충돌 안내.

### M4 — 관리 콘솔과 API, 나머지(0.5.0)

범위(시나리오 306–399. 리스너, 부여, 사용자, 세션, 기록, 감사, 상태는
M4-min):

- [ ] OpenAPI가 있는 관리 API: 애플리케이션, 제공자(실행 중 추가, 비활성화, `managed_by = api`로 제거, ADR-0010), 정책, 블랙리스트.
- [ ] 콘솔에서의 부여(부여, 취소, 역할 변경과 그 남용 사례). 브라우저가 아닌 클라이언트를 위한 API 토큰.
- [ ] API 전체를 다루는 영어/한국어 웹 콘솔. 생성 후에는 비밀 정보를 표시하지 않음. 제공자 비밀은 환경 변수 참조로(저장 시 암호화 모드를 채택한다면 여기서 결정).
- [ ] 읽기 감사와 감사 기록 내보내기(백로그 후보. 여기서 결정).

종료: 모든 관리 작업이 콘솔과 API에서 가능하다. 각각의 감사 기록을 검증한다.

### M5 — 확장 지점(0.5.0)

범위(시나리오 400–499):

- [ ] 게이트웨이의 모델을 따르는 격리된 워커 프로세스의 Lua 훅(400–439): 인증 후 클레임 매핑, 추가 인가 입력, 헤더 매핑. Lua가 할 수 없는 것의 명시적 목록(네트워크 없음, 비밀 정보 없음, 업데이트 제어 없음).
- [ ] 로그인 알림 웹훅(440–469): ADR-0009의 이벤트(로그인 성공, 실패, 새 기기, 잠금, 로그아웃, 취소)를 대상별 전달 행에서 `event_id`를 멱등 키로 삼아 최소 1회 전달. HMAC 서명 전달. 데드레터가 있는 제한된 재시도와 적체. 환경에서 읽는 엔드포인트별 비밀. 기본적으로 내부 주소 범위로의 전송 제한.
- [ ] ADR-0008에 따른 2차 인증 메커니즘(470–499): `Factor` 트레이트(등록, 챌린지, 검증, 복구, 관리자 재설정). verify에서 평가하는 애플리케이션별 단계 상승 규칙. TOTP 먼저, WebAuthn 다음, 복구 코드.

종료: 2차 인증을 요구하는 라우트가 1차 인증만 거친 세션을 실환경에서 거부한다. 웹훅 전달을 루프백 수신기와 실제 엔드포인트 하나에 대해 검증한다.

### M6 — 수명 주기와 릴리스(0.6.0)

범위(시나리오 500–599):

- [ ] 게이트웨이의 검증된 설계를 채택한 서명된 자가 업데이트: Ed25519 매니페스트 봉투, GitHub 릴리스 탐색, 다운그레이드 거부, 크기와 리디렉션 제한, 롤백이 있는 원자적 활성화. `hopae update`, `hopae --check-update`, 옵트아웃이 있는 일일 확인 캐시. 컨테이너 배포는 대신 이미지를 교체.
- [ ] 릴리스 파이프라인: CI 빌드 매트릭스, 정적 Linux 바이너리, 릴리스 자산과 `SHA256SUMS`, 오프라인 서명 절차, `release-public-key.txt`.
- [ ] 설정 다시 로드 의미론과 다시 로드 시 사전 점검.

종료: 인스턴스가 서명된 사전 릴리스로 스스로 업데이트하고, 의도적으로 망가뜨린 릴리스는 롤백한다.

### M7 — 확장과 운영(0.7.0)

범위(시나리오 600–699):

- [ ] 다중 인스턴스 운영을 끝까지 문서화: 공유되는 것, 인스턴스 로컬인 것, 필요한 PostgreSQL과 Redis/Valkey 설정. 인스턴스 두 개 위의 게이트웨이 헤어핀 라우트를 통한 verify 고가용성.
- [ ] Prometheus 지표, 상태와 준비 엔드포인트, 구조화된 감사 내보내기.
- [ ] SQLite 저장소의 백업과 복원. 쿠키와 세션 키, 인증 요소 키, 웹훅 비밀의 키 교체.
- [ ] 게이트웨이 설정 소유권 2단계(ADR-0012). 새 ADR로만, 그리고 게이트웨이 변경 HC-7(필드 범위 라우트 쓰기)이 존재한 뒤에만 진행.
- [ ] API 클라이언트 모드(도전 과제): 게이트웨이의 기본 JWT 검증기가 같은 신원으로 API를 보호할 수 있도록 JWKS와 디스커버리를 갖춘 RFC 9068 액세스 토큰 발급.

종료: 인스턴스 두 개의 순차 교체가 세션을 유지한다. 지표와 백업을 실환경에서 검증한다.

### 1.0

M7 이후, 위협 모델, 게이트웨이 계약, 설정 스키마에 대한 전체 적대적 검토 패스에서
열린 S1/S2 발견 사항이 없으면 1.0.0을 냅니다. 1.0부터 설정과 게이트웨이 계약은
메이저 버전에서만 바뀝니다.

## 게이트웨이 변경

게이트웨이에 제안하는 변경은 [게이트웨이 계약](GATEWAY_CONTRACT.md#제안하는-게이트웨이-변경)에
수용 기준과 함께 나열합니다. 이들은 게이트웨이 저장소의 별도 작업으로서
워크트리에서 수행합니다. HC-3(호출자 키를 담은 정적 요청 헤더)은 M1에
필요하며 M1과 함께 만듭니다. HC-12(업스트림 요청에서 Hopae 쿠키 제거)는 세션
핸들이 업스트림에 도달한다는 실제 배포의 발견에 따라 바로 그 뒤를
따릅니다(ADR-0015). 그 뒤의 권장 순서: HC-6(verify 호출의 정규화된
경로와 라우트 ID), HC-8(`retry-after`를 포함한 `429` 중계), HC-4(쿠키
필터링), HC-1(전체 키를 사용하는 결정 마이크로 캐시), HC-2(세대 번호가 붙은
무효화 구독자), HC-9(게이트웨이 전체에서 `x-original-*` 제거), HC-5(네이티브
진입점, 선택), HC-7(필드 범위 라우트 쓰기, 설정 소유권 2단계의 전제 조건).
Hopae는 각 변경에 의존하는 첫 릴리스에서 그 변경에 대한 게이트웨이 계층
시나리오를 추가하고, 그 짝을 계약의 호환성 매트릭스에 기록합니다.

## 교차 시나리오(900–999)

어느 마일스톤에서든 할당합니다: 쿠키 속성, 포털과 콘솔 폼의 CSRF, 응답 보안 헤더,
상수 시간 비교, CSPRNG 사용, 로그의 비밀 정보 처리, 의존성 감사 정책. 어느
마일스톤에서든 보안 관련 변경은 새 시나리오를 추가하기 전에 이 범위에서 기존
시나리오를 먼저 확인합니다.

## 백로그

일정에 없지만, 처음부터 다시 논의하지 않도록 기록합니다.

- 서드파티 애플리케이션을 위한 OIDC 제공자 모드, SAML, SCIM 프로비저닝.
- ADR-0013 경계 뒤의 범용 forward-auth 어댑터 프로필(nginx `auth_request`, Traefik, Caddy, Envoy `ext_authz`).
- 기기 인가 흐름, 패스키 우선 로그인.
- 형제 서브도메인을 위한 `Domain=` 쿠키 모드(쿠키 토싱 때문에 M1에서 기각).
- 애플리케이션의 접미사 호스트 패턴(`*.example.test`)(기각: 방치된 서브도메인이 자격 증명 목적지가 됨).
- Redis를 세션 상태의 긍정 캐시로 쓰는 것(기각: 여전히 응답하는 오래된 항목이 모든 취소 한계를 넘어 살아남음).
- 게이트웨이 마이크로 캐시의 거부 결정 캐싱.
- 단계 상승에 입력되는 지리적 신호와 새 기기 위험 신호. 애플리케이션별 `max_auth_age`.
- verify 호출에 `sec-purpose`를 전달하여 프리페치와 프리렌더가 문서 탐색으로 집계되지 않게 하는 것(`apps[].logout_confirm = false`와 관련). 모든 라우트 조각을 바꾸는 계약 마이너 변경.
- 콘솔에서 입력하는 저장 시 암호화된 제공자 비밀.
