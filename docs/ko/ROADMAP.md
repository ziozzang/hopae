# 로드맵

<!-- translation-status: source=../ROADMAP.md source-rev=1 status=current -->

[문서 목차](README.md) · [English](../ROADMAP.md)

이 페이지는 작업의 순서를 정합니다. 프로젝트 브리프와 게이트웨이의 기존 기능
조사에서 도출했으며, 마일스톤의 범위나 순서가 바뀔 때마다 갱신합니다. 완료된
항목은 [CHANGELOG](../../CHANGELOG.md)로 옮깁니다. 시나리오 번호 범위는
[`scenarios/README.md`](../../scenarios/README.md)에 정의되어 있습니다.

## 제품의 형태

Hopae는 Hangang 게이트웨이 앞에 서는 것이 아니라 게이트웨이를 **중심으로**
패키징됩니다. 게이트웨이는 이미 외부 인증 확인을 수행하고, 검증된 신원 헤더를
업스트림 요청에 주입하며, 클라이언트가 보낸 복사본을 제거합니다. Hopae는
게이트웨이에 없는 것, 즉 로그인 포털, 제공자, 세션, 정책을 제공합니다.

```text
 브라우저               Hangang(게이트웨이)                    Hopae                      제공자
   │  GET app.example.test/admin  │                              │                          │
   ├─────────────────────────────▶│  포워드 인증 GET /verify       │                          │
   │                              ├─────────────────────────────▶│ 세션 없음                 │
   │  302 auth.example.test/login │◀─────────────────────────────┤ 302 + 돌아갈 URL          │
   │◀─────────────────────────────┤                              │                          │
   │  GET auth.example.test/login (같은 게이트웨이의 라우트)        │                          │
   ├─────────────────────────────▶├─────────────────────────────▶│ 제공자로 302              │
   │◀─────────────────────────────┴──────────────────────────────┤                          │
   ├──────────────────────────────── 인가, 동의 ────────────────────────────────────────────▶│
   │◀─────────────────────────────── 302 /callback?code ────────────────────────────────────┤
   ├─────────────────────────────▶├─────────────────────────────▶│ code → 토큰, 세션 생성     │
   │  302 app.example.test/admin  │                              │ Set-Cookie               │
   │◀─────────────────────────────┴──────────────────────────────┤                          │
   ├─────────────────────────────▶│  포워드 인증 GET /verify       │                          │
   │                              ├─────────────────────────────▶│ 세션 유효                 │
   │                              │  2xx + 신원 헤더              │                          │
   │                              │◀─────────────────────────────┤                          │
   │                              ├── x-forwarded-user 등을 담은 업스트림 요청 ──▶ 앱        │
   │                              │   (클라이언트가 보낸 해당 헤더 복사본은 제거됨)             │
```

로드맵이 의존하는 사실들입니다. 2026-10-09 기준 게이트웨이에서 관찰했으며, 이에
의존하는 각 마일스톤의 G1에서 다시 확인합니다.

- 게이트웨이의 외부 확인은 본문 없는 고정 URL `GET`입니다. 나열된 클라이언트 헤더(세션 쿠키 포함)만 전달되고, 원래 URL, 메서드, 클라이언트 IP 같은 게이트웨이 생성 맥락 헤더가 더해집니다.
- `2xx` 응답은 요청을 허용하고 나열된 응답 헤더를 업스트림에 주입합니다. `302`/`401`/`403` 응답은 `Location`과 `Set-Cookie`와 함께 브라우저로 중계될 수 있습니다. 타임아웃을 포함한 그 밖의 모든 경우는 거부 처리됩니다.
- 어떤 라우트의 응답 목록에든 선언된 신원 헤더 이름은 게이트웨이 전체에서 모든 수신 요청으로부터 제거됩니다.
- 게이트웨이는 인증 결정을 캐시하지 않습니다. `/verify`는 모든 요청마다 호출되므로 빨라야 하며, 취소(revocation)가 동작하는 이유도 이것입니다.
- 경로 범위 지정은 라우트 단위입니다(`path_prefix`, 매칭 모드, 우선순위). 더 세밀한 규칙은 원래 URL 헤더를 사용해 Hopae 안에 둡니다.
- 로그인 제한, 블랙리스트, 로그인 기록은 게이트웨이 기능이 아닙니다. 게이트웨이의 URL별 실패 차단은 바깥 계층이 될 수 있습니다.

## 마일스톤

각 마일스톤은 범위 안의 모든 시나리오가 `verified-live`(또는 사유를 기록한
`implemented`)이고, 두 언어의 문서, 위협 모델 갱신, CHANGELOG 절, G9에 따른
배포가 있을 때 끝납니다. 버전은 참고용입니다.

### M0 — 기반(0.0.x)

목표: 빈 크레이트 위에서 프로세스가 끝까지 돌아간다.

- [ ] Cargo 워크스페이스, [이름이 정해진 대상](PROCESS.md#make-대상)을 가진 `Makefile`, 사전 커밋 훅(비밀 정보 스캔, 공개 검사), `make gates`를 실행하는 CI.
- [ ] [문서 체계](DOCUMENTATION.md#검증)에 명시한 `tools/check_docs.py`와 `tools/scenario_coverage.py`.
- [ ] 프로세스에 나열한 오동작 프로필을 갖춘 `tests/support/mock_idp`의 모의 OAuth/OIDC 제공자.
- [ ] Hopae 바이너리를 실행하고 탐침하는 통합 하네스. `HOPAE_E2E_GATEWAY_BINARY` 뒤의 게이트웨이 계층.
- [ ] `docs/THREAT_MODEL.md` v0: 자산, 신뢰 경계, 공격자 모델, 진입점.
- [ ] 적대적 설계 검토 후 수락된 핵심 ADR: 런타임과 크레이트 선택, 저장소 엔진, 포털 호스트와 애플리케이션 호스트에 걸친 세션 모델과 쿠키 범위, 검증 엔드포인트와 포털 경로, 신원 헤더 이름과 게이트웨이 계약, 돌아갈 URL 검증, **이벤트 모델**(나중에 로그인 기록과 웹훅이 소비), 그리고 M5에서 세션 스키마를 뜯어고치지 않도록 **2차 인증 확장 지점**(세션이 어떤 인증 요소를 언제 충족했는지 기록).
- [ ] `docs/GATEWAY_CONTRACT.md`와 `docs/CONFIG.md` 골격.

종료: 빈 크레이트에서 `make gates` 통과. 템플릿 시나리오 하나가 하네스 위에서 실행된다.

### M1 — 수직 슬라이스(0.1.0)

목표: 실제 사용자 한 명이 실제 게이트웨이를 거쳐 실제 제공자 하나로 로그인하고,
업스트림 애플리케이션이 검증된 신원 헤더를 받는다. 이 마일스톤은 의도적으로
좁으며, 어떤 폭 확장보다 먼저 완료합니다.

범위(시나리오 001–099):

- [ ] PKCE와 nonce를 사용하는 범용 OIDC authorization-code 클라이언트. 첫 설정 제공자는 Google.
- [ ] 내장 저장소의 서버 측 세션. M0에서 정한 속성을 가진 불투명 세션 쿠키. 유휴 수명과 절대 수명.
- [ ] 게이트웨이용 `GET /verify`: 유효한 세션이면 신원 헤더와 함께 `2xx`, 아니면 검증된 돌아갈 URL과 함께 포털로 `302`. 저장소 오류 시 거부 처리.
- [ ] 자체 호스트(문서에서는 `auth.example.test`)의 포털. 같은 게이트웨이의 라우트로 제공: 로그인, 제공자 콜백, 로그아웃, 상태 확인.
- [ ] 헤더 주입 계약: 신원 헤더 집합, 클라이언트 복사본이 게이트웨이 전체에서 제거되도록 하는 게이트웨이 라우트 선언, 위조된 헤더가 업스트림에 절대 도달하지 않음을 증명하는 게이트웨이 계층 테스트.
- [ ] 게이트웨이 라우트를 통한 경로 범위 보호(공개 접두사, 보호 접두사, 더 높은 우선순위의 `/admin`)를 동작하는 라우트 예제와 함께 문서화. Hopae 측 경로별 규칙은 M2로 유예.
- [ ] 설정 파일, `hopae --check` 사전 점검, 사유 코드가 있는 구조화된 로그.
- [ ] Hopae를 게이트웨이 뒤에 두는 `deploy/` Compose 템플릿. 기준 환경에 배포.

참고용 시나리오: 001 게이트웨이 리디렉션을 통한 로그인; 002 유효한 세션의 verify;
003 세션 없는 verify; 004 돌아갈 URL 검증; 005 로그아웃; 006 라우트를 통한 경로
범위; 007 헤더 주입과 위조 제거; 008 쿠키 속성과 호스트 간 범위; 009 제공자 실패
양상; 010 사전 점검과 시작. 최종 할당은 G3에서 합니다.

종료: 실제 게이트웨이의 보호된 라우트에서 브라우저가 실제 제공자로 로그인을
완료하고, 업스트림이 신원 헤더를 보며, 클라이언트가 보낸 신원 헤더는 제거되고,
로그아웃하면 다음 요청부터 접근이 끝난다.

### M2 — 세션과 남용 제어(0.2.0)

범위(시나리오 100–199):

- [ ] 로그인 기록: 제공자, 주체, 클라이언트 IP, 사용자 에이전트, 결정과 사유 코드를 담은 영속 이벤트(성공, 실패, 로그아웃, 취소). 보존 기간 제한.
- [ ] 블랙리스트: 주체, 이메일, 이메일 도메인, 클라이언트 IP(CIDR). 로그인과 `/verify`에서 검사. 관리자가 관리.
- [ ] 계정별, 클라이언트 IP별 로그인 시도 제한과 잠금. 일정한 작업량의 응답. 게이트웨이의 실패 차단과의 상호작용 문서화.
- [ ] 다중 인스턴스 배포를 위한 Redis/Valkey 공유 세션 캐시: write-through, 제한된 로컬 캐시, 거부 처리 의미론, 네임스페이스 격리.
- [ ] 모든 기기에서 로그아웃과 관리자 취소. 주체별 세션 목록.
- [ ] 원래 URL 헤더로 평가하는 Hopae 측 경로와 호스트 정책 규칙(허용, 로그인 필요, 그룹 필요).

종료: 게이트웨이 뒤의 Hopae 인스턴스 두 개가 세션을 공유한다. 잠금, 블랙리스트, 취소를 실환경에서 검증한다.

### M3 — 제공자(0.3.0)

범위(시나리오 200–299):

- [ ] 카카오와 네이버(제공자별 사용자 정보 매핑과 검증된 이메일 규칙을 가진 OAuth 2.0).
- [ ] 이메일 매직 링크: 일회용, 짧은 수명, 요청한 브라우저에 바인딩. SMTP 설정. 속도 제한.
- [ ] 이메일과 비밀번호: Argon2id, 알 수 없는 계정에 대한 더미 해시 타이밍, 재설정 흐름, 비밀번호 정책.
- [ ] 실행 중 제공자 활성화/비활성화와 순서 지정. 제공자별 허용 이메일 도메인.
- [ ] 계정 연결 정책(두 제공자가 한 계정에 대응될 수 있는 조건)을 구현 전에 ADR로 기록.

종료: 테스트 테넌트가 있는 제공자는 각각 실환경에서 검증. 이메일 흐름은 루프백 SMTP 싱크와 실제 메일함 하나에 대해 검증.

### M4 — 관리 콘솔과 API(0.4.0)

범위(시나리오 300–399):

- [ ] OpenAPI가 있는 관리 API: 사용자, 세션, 제공자, 정책, 블랙리스트, 로그인 기록, 감사.
- [ ] 관리자 계정과 역할. 부트스트랩 절차. 자체 리스너나 호스트의 관리 표면.
- [ ] API를 모두 다루는 영어/한국어 웹 콘솔. CSRF와 출처 검사. 생성 후에는 비밀 정보를 표시하지 않음.
- [ ] 영속적인 관리자 감사 로그.

종료: 모든 관리 작업이 콘솔과 API에서 가능하다. 각각의 감사 기록을 검증한다.

### M5 — 확장 지점(0.5.0)

범위(시나리오 400–499):

- [ ] 게이트웨이의 모델을 따르는 격리된 워커 프로세스의 Lua 훅(400–439): 인증 후 클레임 매핑, 추가 인가 입력, 헤더 매핑. Lua가 할 수 없는 것의 명시적 목록(네트워크 없음, 비밀 정보 없음, 업데이트 제어 없음).
- [ ] 로그인 알림 웹훅(440–469): M0 이벤트 모델의 이벤트(로그인 성공, 실패, 새 기기, 잠금, 로그아웃, 취소). HMAC 서명 전달. 제한된 재시도. 환경에서 읽는 엔드포인트별 비밀. 기본적으로 내부 주소 범위로의 전송 제한.
- [ ] 2차 인증 메커니즘(470–499): 인증 요소 인터페이스(등록, 챌린지, 검증, 복구, 관리자 재설정). 세션이 충족한 요소와 시각을 기록. `/verify`에서 평가하는 호스트, 경로, 그룹별 단계 상승(step-up) 정책. TOTP 먼저, WebAuthn 다음, 복구 코드.

종료: 2차 인증을 요구하는 라우트가 1차 인증만 거친 세션을 실환경에서 거부한다. 웹훅 전달을 루프백 수신기와 실제 엔드포인트 하나에 대해 검증한다.

### M6 — 수명 주기와 릴리스(0.6.0)

범위(시나리오 500–599):

- [ ] 게이트웨이의 검증된 설계를 채택한 서명된 자가 업데이트: Ed25519 매니페스트 봉투, GitHub 릴리스 탐색, 다운그레이드 거부, 크기와 리디렉션 제한, 롤백이 있는 원자적 활성화. `hopae update`, `hopae --check-update`, 옵트아웃이 있는 일일 확인 캐시. 컨테이너 배포는 대신 이미지를 교체.
- [ ] 릴리스 파이프라인: CI 빌드 매트릭스, 정적 Linux 바이너리, 릴리스 자산과 `SHA256SUMS`, 오프라인 서명 절차, `release-public-key.txt`.
- [ ] 설정 다시 로드 의미론과 다시 로드 시 사전 점검.

종료: 인스턴스가 서명된 사전 릴리스로 스스로 업데이트하고, 의도적으로 망가뜨린 릴리스는 롤백한다.

### M7 — 확장과 운영(0.7.0)

범위(시나리오 600–699):

- [ ] 다중 인스턴스 운영을 끝까지 문서화: 공유되는 것, 인스턴스 로컬인 것, 필요한 Redis/Valkey 설정.
- [ ] Prometheus 지표, 상태와 준비 엔드포인트, 구조화된 감사 내보내기.
- [ ] 내장 저장소의 백업과 복원. 쿠키와 세션 키, 웹훅 비밀의 키 교체.
