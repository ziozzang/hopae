# Native Human current capture (private prerequisite)

This source boundary joins actual native authentication to Engine Allow and a private current-owner result. It does not activate a Human RPC, SDK assertion, signed receipt, Pumgye grant, projection or Hangang dispatch. Existing ordinary verification and public provider/session interfaces remain compatible. No client header enables capture; only a crate-private owning adapter extension can request it. Ordinary requests do not run the extra current-owner SQL checks. A missing or unsupported BOOTTIME clock refuses this additive path without disabling ordinary authentication.

The owning gateway captures original BOOTTIME admission before caller checks, parsing and awaits. Its bound is the original native verification budget, capped below one second with millisecond quantization charged conservatively. Queueing, parsing, scheduler pauses, suspend and later observations cannot restart that bound. The same actual caller-key and request parser feed the native session Engine. Service credentials and Workload attempts cannot be promoted through this path. The result binds the presented handle digest, URL, canonical path, method, host/port, caller slot, route, client IP and user agent. The native session parser has no final body/allowlisted-header digest: **this private candidate is not bound to that final request digest**. A future owning Human RPC must supply and verify that boundary before any signed proof. An empty-body assumption is not made.

Only the ordinary final Allow branch retains its exact HandleView and effective native lifetime. When authorization changes use Refresh, the witness retains the exact refreshed session identity snapshot and expected authorization version, rather than the older lookup row. Terminate keeps its existing policy. Login redirects, handoff redemption, entry routes, denials and step-up requests do not produce a candidate. Capture uses the owner's actual Store directory/session implementations; public caller-built identities or alternate session traits cannot supply its positive source.

## Original primary and TOTP authentication

Schema 9 adds `session_primary_provenance`, without backfilling legacy sessions. The actual SessionService captures the exact compiled provider Arc and prepared owner before adapter verification. Only successful native password verification or OIDC completion constructs the private, non-cloneable verified primary command. In the same existing session-create or actual reauthentication transaction, SQLite checks the original provider incarnation and config generation, identity-to-user relationship and pure retained publication fences, then records the establishing primary factor and authentication metadata. A provider/config change or ABA during verification cannot attach a new qualified record. Provenance insertion failure rolls back session/handle/login-consumption changes. Earlier identity/user resolution remains its existing separate transaction and may leave an orphan user after failure.

The primary record retains its establishing credential generation. TOTP increases the session generation while preserving that original primary record and authentication time. Actual qualified primary reauthentication replaces the record only with a strictly newer generation. Legacy or unqualified primary reauthentication deletes any earlier primary record in that same transaction, even when the authentication time rounds to the same second. A legacy session, deleted link, pre-change provider session or previous configuration generation remains ordinary-compatible but cannot borrow today's prepared Registry to become qualified. A fresh native reauthentication is required. Google forced reauthentication remains unsupported as already declared by its provider capability; this feature does not change it.


The optional top-level `human_material_key_env` names a dedicated, shared source-domain key: exactly 32 securely generated bytes encoded as canonical unpadded base64url (43 characters). It is independent of gateway caller keys. Absence, unavailable/invalid material or an all-zero key leaves ordinary authentication usable but disables this additive Human qualification. A malformed environment reference is rejected without echoing a literal. The key is resolved once at startup; no raw-key, unkeyed digest or process-random fallback exists. Its lifecycle belongs to the authoritative source domain: all replicas must use consistent key/provider secret/CA material. Rotating it retires earlier material qualifiers and requires actual native primary reauthentication.

Schema 9 also adds permanent monotonic `human_provider_material_owners` tombstones. Provider compilation MACs the exact resolved OIDC settings/secret or LDAP settings/password/validated CA bytes it consumes. CA data is bounded and opened once; the MAC and TLS roots use the same immutable bytes. Only an actually usable compiled provider can publish a material owner. No provider secret, enrollment seed or CA content is persisted in this ledger; the stored fingerprint is keyed and opaque. The primary record retains its original material revision. Replacing contents at the same env reference or CA path, disable/re-enable and A→B→A therefore cannot adopt earlier primary evidence. Truly unchanged material/key/provider/configuration across an ordinary Store reopen keeps the revision stable and may qualify a still-current durable native session; a private Checked object cannot cross processes. No blanket restart reauthentication rule is implied.

Preparation captures provider rows/incarnations, config generation and the material-ledger snapshot together before compiling. Publication uses a bounded SQLite writer CAS against those original owners and expected material revision. An identical concurrent preparation may share precisely the anticipated single transition; equal MAC bytes after an intervening ABA do not qualify. Stale prepared publishers fail closed instead of overwriting a newer owner. Unchanged preparations/imports do not rotate material revisions. Tombstones cannot be deleted or rewound, and capacity/revision exhaustion refuses publication. No environment/file/network callbacks run under the writer transaction. Final source checks remain point-in-time across memory and SQLite, and failure after a durable material publication may conservatively leave the additive path unavailable. This ledger does not establish a distributed desired-material authority or resolve inconsistent out-of-band replica secrets; operators must publish consistent material through the owning lifecycle. Arbitrary backup rollback, independent cloned ledgers and unfenced live-owner clones remain unqualified.

For handle AAL2, the existing exact native TOTP association is mandatory: original enrollment ID/revision, session generation, factor index/time and config generation must remain current. The original primary record must also remain current. A newer External/Recovery/WebAuthn factor cannot freshen old TOTP evidence; every matching freshness rule is reevaluated using the qualified factor, and its original deadline caps the candidate. Another session advancing the enrollment counter alone does not retire the enrollment. No seed, password, OTP code, raw cookie or provider secret is stored in these provenance records or serialized by the candidate. TOTP enrollment setup in the owned tests uses encrypted fixture seed installation; the actual cryptographic elevation, portal-handle rotation and app handoff are exercised, not a claim that enrollment UI was qualified.

## Current checks and qualification limits

One bounded SQLite read transaction compares the exact handle/session/user/identity relationship, primary record, current provider incarnation, exact compiled-material revision/MAC and config generation, and TOTP association when required. The earlier effective expiry cannot be extended by handle touch. Native wall callbacks run before this joined read; afterward only the actual BOOTTIME backend and retained publication/retirement checks run. A sibling check retiring the candidate is observed before success. These are point-in-time checks, not atomic authorization across unrelated owners or remote services. No callbacks or network exchanges are added under the joined read transaction.

The resulting private type is non-serializable and has no public constructor. Every later consumer must repeat current owners and the original age fence. There is no issued Human observation record, durable proof/replay protocol or externally usable grant in this stage. Durable SQL reads are a correctness foundation; source-backed immutable memory snapshots, membership/follower gates and throughput qualification remain pending. No live remote LDAP account-withdrawal or Google account acceptance claim follows from a local session check. Password form support continues to use LDAP, not a self-owned password database. Unseen privileged same-generation publisher replacement, arbitrary database rollback, live VM clones and shared-ledger fencing are not qualified.

A compiled CLI child-process test uses the same config file and Store across graceful exit/restart: unchanged material preserves the owner, while same-reference secret changes/ABA and dedicated-key rotation retire it without a configuration-generation change. Native durable-primary recapture after unchanged Store reopen is tested separately.

Tests exercise actual production OIDC discovery/JWKS/RS256, nonce/PKCE and native SessionService completion; actual owned OpenLDAP LDAPS and mandatory StartTLS; real TOTP elevation and native handoff; Engine Allow; owning gateway caller/parser capture; current-owner revocation, primary ABA/config-generation refusal, actual primary reauthentication, SQL rollback, refresh expected-state retention, deadline/cancellation/suspend/clock failure and concurrent retirement. The local OIDC issuer uses explicitly permitted loopback HTTP with `allow_private_endpoints`, not disabled TLS verification or public-provider acceptance. The owned LDAP test is separately provisioned and run; a normal full-suite ignored result alone does not qualify that external fixture. Operating adoption, final Human wire/full-chain tests and the broader mixed-identity objective remain separate gates.
