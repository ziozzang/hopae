# Human durable identity storage foundation (schema10)

This is storage/H0 groundwork, not Human RPC, receipt, subject lookup or runtime route activation. Existing ordinary login requires no new issuer/realm configuration. No global UserId parser or legacy stored-ID syntax changes.

Migration0010 atomically creates a Store-owned public authority realm from32 random bytes as64 lowercase hexadecimal characters, nonzero, and seeds an append-only historical user-ID reservation set from all currently live users. The realm is an identity namespace, not a secret/signing key or proof. Before-insert guards reject replacement of the singleton realm and existing reservations even when SQLite recursive_triggers is off; update/delete guards preserve both. Users retain immutable primary keys. Every new user INSERT reserves its exact ID in the same transaction; any INSERT/REPLACE reuse of a historical ID refuses, including after deletion. No FK removes reservations. Failed user creation rolls back its identity/events with the transaction.

History starts at schema10. IDs deleted before migration cannot be reconstructed, but the new realm precedes any future Human subject namespace using this foundation. Existing live arbitrary legacy IDs are backfilled unchanged; no canonical-subject function or configured issuer binding is introduced here. Explicit identity linking retains the same native user ID; disabling the user still uses existing authz/session revocation. An identity cannot be established by merely submitting a UserId or realm to a new public API: none is added.

Normal application startup retains its existing lock → read-only precheck → consistent pre-migration backup → Store migration order. Store::open itself is a lower-level migration API and does not independently create that application backup. Version10 precheck verifies exact tables/guards, preserving quoted SQL literal case/whitespace (including GLOB semantics), the singleton realm and coverage of all live users. Missing or damaged guards/records refuse rather than repair history. Migration failure rolls back, with no zero/legacy fallback realm. Older binaries reject schema10: binary-only rollback after migration is unsafe; preserve and deliberately restore a consistent pre-migration database backup with all writers stopped. No hot rollback, independent clone, malicious SQL/DROP or external fencing guarantee is claimed.

The actual native H0 `require_human_snapshot` retains its existing Store.read_checked SQLite transaction. Its existing main session/user/provider SELECT additionally joins the reservation and realm singleton, then includes the exact realm in private Current equality. This is still SQL-backed, not a zero-query or immutable-memory hot path, and adds no separate asynchronous Store call/network query. Existing provider/material/factor/session/handle/app/time/source checks remain required. The authority realm alone is no authentication capability and no subject/issuer constructor is exposed.

Tests exercise actual Directory creation/linking, deterministic random-ID collision after hard deletion, reopening with stable realm, live and historical REPLACE refusal, immutable PK, schema9 live-ID backfill, malformed/missing guards and quote-sensitive validation, zero-realm transactional failure, and actual native OIDC/Engine Current retirement on deliberately fault-injected realm change. The privileged fault injection tests field comparison/retirement only, not support for running on a tampered or cloned database. Broader Human identity/subject/receipt design remains separate.
